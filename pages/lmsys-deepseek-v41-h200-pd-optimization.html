DeepSeek-V4.1 H200 PD 分离优化：六处改动，端到端延迟最多降 63.9%

  • 原文：Optimizing DeepSeek-V4.1 on H200 with SGLang PD Disaggregation（LMSYS 博客，2026-11-05）
  • 主题：推理优化、并行策略（PD 分离）、GPU kernel、SGLang、MoE、投机解码
  • 星级：⭐⭐⭐⭐（重点阅读）
  • 一句话要点：DeepSeek-V4.1-Flash 在 8 卡 H200 的 SGLang 1P1D 部署上，Indexer 一次前向占 209.47 毫秒（约 39%）；六处改动——打分宽度对齐、只算候选位置、融合打分后处理、Prefill 块放大到 16K、MoE 输出改 reduce-scatter、有界重放接 CP 与 DSpark——让端到端延迟降 15% 至 64%，TTFT 降 41% 至 79%，代价是 TPOT 全线上涨 2.6% 至 51.9%，GSM8K 从 96.74% 降到 95.38%。

核心结论

部署是 8 卡 H200 上的 SGLang 1P1D 配置：Prefill 占 4 卡（TP4/CP4/EP4），Decode 占 4 卡（TP4/DP4/EP4）。瓶颈先出现在 Prefill 侧：并发不高时请求已经在 Prefill 队列里积压，Decode 侧的可用缓存容量解释不了排队。一次代表性早期画像里，Indexer 占 209.47 毫秒，约占单次前向拆解的 39.06%；MoE 计算与 NCCL 各占约 18%。

六处改动各啃一块成本，都有独立的基准对照，百分比不能跨行相加：

改动 啃掉的成本 收益
打分宽度对齐 GEMM 的物理形状 微基准打分延迟降约 40%
只算候选位置 打分的键集合 端到端降幅最高 22.1%
融合打分后处理 打分后的访存流量 端到端降幅最高 18.2%
Prefill 块 8K → 16K 调度轮数 TTFT 最高降 31.3%
MoE 输出改 reduce-scatter MoE 输出归属 每 rank 通信时间降 19.4% 至 21.7%
有界重放接 CP 与 DSpark 后 19 层算多少 token TTFT 降幅最高 46.7%

合并之后，8 组缓存命中率与并发组合里端到端延迟降 15% 至 64%，TTFT 降 41% 至 79%，最大端到端降幅 63.9%（70% 命中、并发 16，基线/合并延迟比 2.77），最大 TTFT 降幅 79.0%（90% 命中、并发 32）。代价在生成侧：TPOT 在 8 组工况里全部上涨 2.6% 至 51.9%，GSM8K 从 96.74% 降到 95.38%，低 1.36 个百分点，原因没有确认，有界重放的边界近似是头号嫌疑。

测量口径

输入名义上是 65,536 token，输出 512 token；缓存命中率标签 50%、70%、90% 对应共享前缀 32,768、46,080、61,440 token，并发分别是 4 与 8、8 与 16、8、16、24 与 32。每个工况跑三次，每次 512 个请求加 10 个热身请求；TTFT、TPOT、E2E 取三次运行均值的均值与样本标准差（ddof=1）。优化前基线测在开发起点 commit d0a7565，滑动窗口有界重放关闭，两个 Prefill token 上限都是 8,192。基线 GSM8K 是 1,319 道单样本题，96.74%。

第 1 至 3 节从共同起点独立评各自改动；第 4 节在三处 Indexer 改动合并的基础上评大块；第 5 与第 6 节各自在第 1 至 4 节的基础上再加一处。有些表的逐次 SGLang 版本记录没有保留，复现时以各节开头的基线与优化配置为准。

模型机理：Indexer、共享候选与有界重放

DeepSeek-V4.1 把 128 位置滑动窗口与稀疏访问压缩历史结合：部分源层产出压缩 KV 与 Indexer 键，消费者复用最新源层存下的历史，同时维护自己的局部窗口 KV。最后一个压缩 KV 源层是第 20 层，第 21 至 39 层不用再产出新的压缩表示就能读这段历史。

Indexer 决定注意力读哪些压缩历史位置。BF16 路径上，Indexer 对每个头算查询与键的点积，过 ReLU 与查询相关的头权重，再沿头求和，最后做 top-k 选择。第 20 层最多发布 2,048 个候选块，每块 8 个压缩位置，同时从全部可见位置里给自己选 top-512。后面的 Indexer 源层共享这些候选块 ID，在这个域里算自己的分数与最终 top-k，不复制发布者的分数与最终 top-k。没有自己 Indexer 的层复用最近一次选择。

有界重放利用固定的后层压缩历史，把第 21 至 39 层的 Prefill 计算限制在每请求尾部窗口：整块提示词先过第 0 至 20 层，后 19 层最多只执行每请求最后 128 token；128 是配置的滑动窗口长度，不是 CP 分区大小，也不是 Indexer 的 top-k 预算。DSpark 是推测式块起草器，用目标模型选定层的隐藏状态填充草稿 KV 状态并约束提案。

第一招：把 BF16 打分宽度补齐到 64 的倍数

相邻的 Indexer 打分宽度，GEMM 代价可能差很多：跨 rank 画像显示，64 对齐的宽度比相邻未对齐宽度快得多。打分操作的大中间张量形状是 [查询行，头数，可见键数]，把物理键范围补齐能改善 GEMM 形状，多算的算术量很小：多一列就把宽度 28,799 变成 28,800，即 64 的倍数。

CUDA BF16 键、可见位置不少于 1,024 时，改动把反量化后的键张量补齐到 ceil(可见键数 / 64) × 64，每个请求只做一次，查询块之间复用。分数在因果掩码与 top-k 选择之前切回逻辑范围；块大小计算用补齐后的宽度，现有中间显存预算不变。

查询行数 逻辑打分宽度 基线 对齐后 降幅
582 28,799 4.113 ms 2.462 ms 40.1%
292 57,343 4.088 ms 2.472 ms 39.5%
582 28,800 2.443 ms 2.445 ms 基本不变

服务基准里，8 个工况 TTFT 降 12.3% 至 18.2%，E2E 降 4.4% 至 14.8%。50% 缓存命中、并发 4 时，TTFT 从 6,245 毫秒降到 5,108 毫秒，E2E 从 7,402 毫秒降到 6,327 毫秒。CP rank 0 的 trace 在同一逻辑形状下对比，打分核耗时从 1.88 毫秒降到 362 微秒。GSM8K 保持 96.74%。

第二招：只给候选位置打分

原来的 Torch 消费者先给全部可见键打分，再收集候选分数；永远选不上的位置白白消耗 GEMM 算力与中间显存带宽。改动把限制移到打分之前：Triton 核用块 ID 直接加载对应的键，产出宽为 C 而非完整可见宽度 L 的紧凑逐头打分张量。ReLU、头加权与头归约保留原操作；因果掩码与无效候选掩码在 top-k 之前作用于紧凑分数。

小例子：16 个逻辑压缩 Indexer 键位置，编号 0 至 15，发布者给出块 [1, 3]，示例块大小取 4，模型实际用 8。消费者已经被限制在 [4…7, 12…15]；旧实现每头算 16 个分数再收集其中 8 个，新实现直接算 8 个合格分数。紧凑 top-k 选中第 5 列时，候选列表下标是 5 // 4 = 1，对应已发布块 3，块内偏移是 5 % 4 = 1，逻辑键位置因此是 3 × 4 + 1 = 13，再按请求的映射从逻辑键位置 13 落到物理 KV 槽。把紧凑第 5 列当成键位置 5 会选错历史。

优化路径要求 CUDA BF16 操作数、头维 128、头数不多于 64、候选宽度不大于可见键长度的一半；更宽的候选集走原路径。服务基准显示 TTFT 降 22.9% 至 32.5%，E2E 降 8.3% 至 22.1%。70% 命中、并发 8 时，TTFT 从 8,061 毫秒降到 5,944 毫秒，E2E 从 9,228 毫秒降到 7,191 毫秒；90% 命中、并发 16 时，TTFT 从 2,846 毫秒降到 1,922 毫秒，降 32.5%。CP rank 0 打分核耗时从 1.88 毫秒降到 1.147 毫秒。本地验证报告：测试过的模型风格 FP4 输入上分数与 top-k 完全一致，GSM8K 保持 96.74%。

第三招：把打分后处理融进一个 Triton 核

原来的顺序先物化大块 BF16 逐头分数，再过 ReLU、乘头权重、沿头归约、转 FP32。分开的元素操作反复读写 [查询行，头数，上下文] 张量；画像把约 104.8 毫秒的单次代表性前向归于乘法、截断/ReLU 与归约操作。改动保留原来的打分 GEMM，把后面的 epilogue 换成一个 Triton 核，走支持的 32 头 CUDA BF16 路径；GEMM 的逐头输出还在，后面的全尺寸中间张量消失。

数值行为关键，因为 top-k 直接消费这些分数：两个几乎打平的键在选择阈值附近会因为微小舍入变化互换顺序，改变注意力读哪些 KV 条目。核在乘法与归约之后保留 BF16 舍入，用 4 个交错累加器复现测试过的 Torch/CUDA 32 头累加顺序。最后转 FP32 恢复不了更早一次 BF16 转换已丢的精度；公式相同，改了舍入点或求和顺序就可能改变选择。上下文相关的行步长与头步长仍是运行时参数，不给每个上下文相关步长单独特化核；不支持的设备、数据类型、头数、宽度与版式走 Torch 回退。

服务基准显示 TTFT 降 19.8% 至 25.8%，E2E 降 4.3% 至 18.2%。50% 命中、并发 4 时，TTFT 从 6,245 毫秒降到 4,850 毫秒，E2E 从 7,402 毫秒降到 6,099 毫秒。选中的 CP rank 0 trace 区间覆盖 GEMM 与打分后处理，从 4.243 毫秒降到 2.26 毫秒。GSM8K 是 96.59%，基线两次运行分别是 96.74% 与 96.36%。

三处改动能不能叠加由调用路径决定：对齐与融合可在符合条件的稠密路径上叠加；候选打分替换稠密 GEMM，核查的实现不调融合 epilogue。把第 1 至 3 节的优化一起 cherry-pick 到 commit d0a7565 上，用 8K Prefill 块评合并配置：相对共同早期基线，TTFT 降 29.7% 至 46.3%，E2E 降 9.5% 至 34.5%，TPOT 涨 8.1% 至 20.6%。这组合并配置是第 4 节的基线。

第四招：Prefill 块从 8K 放大到 16K

8,192 token 的块处理长未缓存后缀要走多次 Prefill 前向与调度轮次；块放大到 16,384 token，每次前向处理更多后缀，轮次减少。TTFT 在每个显示工况都下降，最大降幅 31.3%（90% 命中、并发 24）；E2E 在 8 个工况里 7 个改善，最大降幅 15.8%（90% 命中、并发 32）；50% 与 70% 命中时 TPOT 也降约 20.1% 至 21.4%。

90% 命中、并发 16 时例外：TTFT 只改善 4.1%，TPOT 涨 7.4%，生成侧的增加盖过输入侧的收益，E2E 从 3,396 毫秒升到 3,471 毫秒，回退 2.2%。TTFT 降而 TPOT 涨的工况里，服务指标显示 Prefill 块放大后，每个 Decode DP rank 上平均运行请求数增加约 10% 至 20%：更快的 Prefill 把请求更早送到 Decode，生成期间每 rank 上同时活跃的请求更多，可能是 TPOT 上涨的原因之一。第 4 节配置的 GSM8K 是 96.59%，截断输出率 0.15%。

同一次调查还暴露了 Decode 侧的 CUDA 图元数据问题：捕获期间把 CUDA 序列长度读回主机可能失败，迫使元数据路径走 eager 执行。已合入的改动在后端需要主机序列长度时不运行草稿元数据粘合图，并删掉 Decode 图捕获期间一次没用的序列长度求和读取；当前 DSpark 配置下主机长度守卫是防御性的。

第五招：MoE 输出改用 reduce-scatter

DeepSeek-V4.1 的 CP MoE 返回路径上，原来先对完整专家输出做全归约：每个 rank 拿到全部归约后的行，再选自己的 CP 分片并做连续化。TP=CP=4 且同组 GPU 时，每个 rank 最终只要其中四分之一的行。

关键在版式：启动选项 --cp-strategy interleave 把原始提示词位置轮流分给 CP rank；MoE 之前按 rank 顺序打包本地分片，每个 rank 的行因此在收集后的缓冲里占一块连续区域，哪怕原始提示词位置是交错的。16 个 token、CP4 时缓冲是 [0,4,8,12 | 1,5,9,13 | 2,6,10,14 | 3,7,11,15]；rank 0 拥有前 4 个缓冲行，对应提示词位置 [0,4,8,12]。模型按 model_type == "deepseek_v41" 设置 cp_return_contiguous，与 CLI 策略名无关。

4 个 rank 时，记 rank r 的部分整行输出为 Y_r，四者之和为 Y = [S0 | S1 | S2 | S3]。全归约让每个 rank 收到全部 4 个归约分片，再只留 S_r；reduce-scatter 让 rank 0 只收 S0、rank 1 只收 S1，依此类推。每个 rank 上存的归约输出只有四分之一大——这不等于网络流量少 75%，也不等于延迟降 4 倍。门控要求 CUDA/非 HIP 张量、TP/CP/组大小匹配、行数非零且能被 CP 大小整除。

第六招：有界重放接上 CP 与 DSpark

已有的解码器侧有界重放优化先让第 0 至 20 层处理完整提示词块，再让第 21 至 39 层每请求最多执行最后 128 token。选项名带解码器侧字样，实际开在 Prefill worker 上。

这是尾部边界上的一处近似：尾部起点的保留 token 本来会注意边界之前的一部分局部窗口键，但后层没有重建这些行；隐藏状态因此可能不同，差异会向后层传播。保留压缩长程历史恢复不了省掉的局部窗口计算，也做不到与完整 Prefill 等价。速度与质量的取舍属于有界重放本身。

兼容修复针对的是紧凑输出的收集版式：CP 与 DSpark 辅助状态捕获下，模型返回紧凑尾部输出；eager CP 运行器原来按完整块版式收集。单个 16,384 token 块在 CP4 下，完整版式期望每 rank 4,096 个局部行，128 token 的尾部每 rank 只有 32 行；输出张量与收集元数据描述的 token 集合对不上。单个请求、无缓存前缀、提示词位置从 0 到 16,383 时，紧凑行 0、1、127 对应原始位置 16,256、16,257、16,383。改动加了一个模型专用的 postprocess_cp_output 钩子，用尾部专用的 CP 元数据收集隐藏状态与辅助状态，按原始全局 token 下标对齐 logits 与 DSpark 消费者，并在 finally 块里恢复原始批次元数据。

服务基准报告 TTFT 降 13.6% 至 46.7%。70% 命中、并发 8 时，TTFT 从 4,301 毫秒降到 2,294 毫秒，E2E 从 5,358 毫秒降到 3,588 毫秒；E2E 最大降幅 34.3%，在 50% 命中、并发 8 时。同一张表里，70% 命中、并发 8 的工况 TPOT 从 2.07 毫秒每 token 升到 2.53。改动报告了 4 rank 的 token 映射与元数据恢复验证、9 个全模型功能请求与 32 道 GSM8K 冒烟测试；附带的完整 1,319 道单样本评测是 95.38%，截断输出率 0.08%。滑动窗口有界重放是近似算法，怀疑沿这条执行路径的数值计算差异导致 GSM8K 分数更低，这一点没有经过其他条件匹配、只开关重放的精度对比确认；截图报告平均输入 token 是 86，低于 128 token 的尾部。

复现要点
