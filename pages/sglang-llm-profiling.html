一句话要点

SGLang 内置的 Torch Profiler 加 Perfetto 时间线，能把一次推理拆成 CPU 侧发起与 GPU 侧执行两条线对照。Qwen3.5-0.8B 在单块 L4 上，prefill 的重复峰群与模型 6 组混合块一一对应，decode 则被一连串瘦 GEMV 占满；最贵的一颗核是只跑一次的词表投影 gemv，2063.7 微秒。先算 roofline 再看 trace：batch 1 decode 的带宽上限 187.5 token/s、算力上限 75k token/s，decode 天生靠近显存带宽上限。

核心数字

  • 模型：Qwen3.5-0.8B，隐藏维度 1024，词表 248k，24 层，6 组（3 个门控 DeltaNet + FFN，加 1 个门控注意力 + FFN），上下文 262k token
  • 权重：bf16 下 0.8B 参数占 1.6 GB；L4 带宽 300 GB/s；batch 1 decode 带宽上限 187.5 token/s；算力上限 75k token/s
  • 词表投影：[1, 1024] @ [1024, 248320] = [1, 248320]，grid 31040（248320 / 8），block 8×8，占用率 25%
  • prefill 最贵的核（总耗时 / 次数 / 平均）：gemv 2063.7 微秒 / 1 / 2063.7 微秒；ampere_bf16_s16816gemm_bf16_128x128，1705.4 微秒 / 24 / 71.1 微秒；cutlass_80_wmma_tensorop_bf16_32x32，1553.5 微秒 / 18 / 86.3 微秒；ampere_bf16_s16816gemm_bf16_64x64，848.1 微秒 / 24 / 35.3 微秒
  • 128x128 GEMM 出现 24 次，对应每块一次大的投影式操作；CUTLASS GEMM 出现 18 次，对应 18 个 GDN 块
  • 采样设置：热身 5 步后采 2 步，prefill 与 decode 分两条 trace；提示 45 个 token

先算 roofline 再看 trace

  • 0.8B 参数用 bf16 占 1.6 GB；L4 带宽 300 GB/s，每 token 搬 1.6 GB 权重，带宽上限 187.5 token/s
  • 每 token 的推理开销粗估 2P FLOPs：1.6 GFLOPs，bf16 tensor 吞吐约 121 TFLOPS，算力上限 75k token/s
  • 算力上限比带宽上限高得多，看 trace 之前的出发假设是 batch 1 decode 更靠近显存带宽上限；性能分析要么证实这点，要么解释它为什么错了

启动方法

  • 安装 CUDA toolkit 13.2，用 uv 建虚拟环境装 SGLang（prerelease），sglang serve --model-path Qwen/Qwen3.5-0.8B
  • 性能分析端点 /start_profile：output_dir、热身 5 步、采 2 步、activities 含 CPU 与 GPU、profile_by_stage 为真、record_shapes 与 with_stack 为真
  • 发一个请求：python -m sglang.bench_serving --backend sglang --num-prompts 1
  • CUDA 启动是异步的：CPU 时间线上一颗核出现得早，GPU lane 里它实际跑得晚；读 trace 时 CPU 侧先看谁发起的活，GPU 侧看设备时间花在哪
  • trace 文件在 Perfetto UI 里打开查看

prefill 全景

  • prefill 是模型消费提示词 token 并产出一个 token 的阶段；性能分析器上半是 CPU 侧操作，下半是 GPU 侧操作
  • 峰以 3 个一组出现，中间夹一个小峰；第一个峰比其他的大得多
  • 放大最左侧的小峰：启动 torch profiler、SGLang 准备组装输入 batch、设置 CUDA 数据流，一切就位等前向跑起来
  • 点开一个 CPU 操作，能关联到它发起的那颗核；一次 host 到 device 的拷贝很小，大概是请求元数据、token id 或调度器需要的小张量，从 pinned CPU 内存拷到 GPU

模式一：重复峰群就是 6 组混合块

  • prefill 主计算区的峰群不是随机的，对照模型结构，峰的分组与 6 组混合块正好对上：每组 3 个 GDN 块加 1 个全注意力块，重复 6 次
  • 第一组里的第一个峰比其他的大得多，推测是第一个混合块通常比其他块多一些启动成本
  • 接下来的两个峰是 GDN 块，里面的核包括 causal_conv1d_fn、fused_qkv_split_gdn_prefill、fused_gdn_gating、ChunkGatedDeltaRuleFunction、l2norm_fwd、chunk_local_cumsum、chunk_gated_delta_rule_fwd_kkt_solve、recompute_w_u_fwd、chunk_gated_delta_rule_fwd_h、chunk_fwd_kernel_o；点开 GPU 区域里的核可以验证
  • 较小的第四个峰是全注意力块，用 FlashInfer；提示只有 45 个 token，全注意力并不是瓶颈
  • 核区域里的模式：重复的绿色粗段，末尾一颗大的蓝色核

最后的词表投影：只跑一次却最贵

  • 推过整段重复峰，进入最后一段：服务器转入清理并准备 decode，有最终投影到 logits、采样、把结果拷回 CPU
  • 点开 CPU 侧的 aten::mm，展开参数：输入类型 bf16，输入形状 [1, 1024] 与 [1024, 248320]
  • 概念上是 [1, 1024] @ [1024, 248320] = [1, 248320]；词表太大，这一步变成大规模矩阵向量式投影，整个 prefill 里只跑一次，仍是这一段里最慢的核之一
  • 核的细节：grid [31040, 1, 1]，block [8, 8, 1]，每线程寄存器 168，共享内存 288，占用率 25%；网格形状来自 248320 / 8 = 31040
  • 最终线性头把一个 1024 维隐向量投到很宽的词表维度上；优化这条路的话，值得看这段投影能不能融合，或找类似的优化

prefill 最贵的核

  • gemv 核最贵，尽管只调用一次：2063.7 微秒
  • 128x128 的 BF16 GEMM 出现 24 次，正好对应每个块一次大的投影式操作；较小的 CUTLASS BF16 GEMM 出现 18 次，正好对应 18 个 GDN 块
  • 只看核名会很吵、很难理解，对照模型布局与数据流一起读，trace 就好推理得多

decode：采了两步，所以有两次 pass

  • decode 是另一类工作负载：prefill 处理整个提示序列，很多操作有足够的工作量，能长成像样的 GEMM；decode 在小 batch 下一次只处理一个新 token，很多投影工作塌成瘦矩阵向量操作
  • 高亮区域是重点；周围区域大多是性能分析器的启动/收尾、输入准备、同步与记账，值得理解，但不是模型主计算路径
  • 左边 SGLang 加载 batch，把这一步 decode 的输入拷进固定的 CUDA 图缓冲；中间是真正的 decode 工作；CPU 时间线没有把每个模型层展开成一层层单独的启动，因为 decode 路径用的是 CUDA 图重放
  • 图重放之前有少量小核与拷贝做准备，不是层堆叠，大多在准备被捕获的图所需的固定缓冲与执行状态；点进图重放区域，GPU 核就在这次重放下面露出来

decode 被瘦 GEMV 占满

  • 重复的蓝色条是词表投影附近见过的那个 GEMV 家族；decode 里它们一遍遍出现，因为 batch 1 decode 把很多线性层变成矩阵向量式操作
  • 核心性能问题：GEMV 的算术强度比大 GEMM 低得多，权重从显存大量流过，却没有足够复用来让 tensor core 像 chunky 的 prefill GEMM 那样保持忙碌；哪怕 GPU 算力绰绰有余，decode 路径也会被显存带宽卡住
  • 细小的红绿紫点是混合块里其他核，重要，但这次 batch 1 的 trace 形状主要在讲一件事：decode 路径是一长串瘦投影
  • 增大 batch 会改变局面：batch 一大，有些瘦操作就没那么瘦，工作负载更接近 GEMM 形态，GPU 每搬一字节权重能做更多有用的数学；batch 不是免费的，KV 缓存、时延、调度与显存压力都要算进去，但它解释了单请求 decode 为什么对 GPU 这么难

下一步
