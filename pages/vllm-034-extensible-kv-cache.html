vLLM 0.34：可扩展 KV 缓存删掉 8% 显存预留

  • 原文：vLLM 0.34 stops reserving 8% of your GPU（dev.to，2026-11-16）
  • 作者：wolfsea2357（第三方解读；未在 GPU 上实测 vLLM，数据引自发布说明与四个改动，指标名对照 0.34.0 源码核对过）
  • 主题：KV 缓存、推理优化、vLLM、显存管理
  • 星级：⭐⭐⭐⭐（重点阅读）
  • 一句话要点：0.34 把 KV 缓存定容从估计法改成实测法——虚拟地址整段预留、物理页按需挂接，热身后按实测峰值定容；GB200 上 KV 缓存多 4–10%、启动快 21–34%；块 64 默认值对短请求的前缀命中不友好。

核心结论

vLLM 0.34 之前，KV 缓存大小靠启动时估计：先按 gpu_memory_utilization 0.9 之类的比例留一块显存，再扣掉权重与各种余量，剩下的才分给 KV 缓存，8% 的显存就死在各种预留里。0.34 改成可扩展 KV 缓存：整段虚拟地址先预留（CUDA cuMem / HIP hipMem），物理页只在捕获与热身实际碰到的块上挂接；热身后按实测的瞬时峰值再一次提交最终块数。定容规则：预算 − max（profiling 峰值，热身峰值）− max（1 GiB，0.75×瞬时峰值），取各 worker、各 DP 引擎的最小值。默认只在 CUDA/ROCm + V2 运行器上开启。

实测数据：缓存多 4–10%

GB200 每卡 189 GiB，三组新旧交错配对取中位：

模型 KV 缓存变化 显式 0.92 对比
Qwen3-8B +7.5% −0.6%
Qwen3-32B +9.5% −1.9%
gpt-oss-20b +7.0% −0.9%
Qwen3.6-35B-A3B +8.8% −2.3%
Qwen3-235B-A22B-FP8 +8.2% −1.5%
DeepSeek-V4-Flash +4.1% −3.7%

注意第二列：保留显式 0.92 反而比旧引擎缓存更小，少 0.6–3.7%。显式值现在是硬上限，0.92 的旧习惯在新引擎上是亏的。利用率警告的小跑里，Qwen3.5-0.8B 上显式 0.9 给 23,920 块（157.68 GiB），不设置给 26,200 块（172.71 GiB），差 15.03 GiB。

换算成序列数：按每 token 256 KiB 规划，103.1 GiB 对应 422,297 个 token（约 103 条 4k 序列），113.0 GiB 对应 462,848 个 token（约 113 条）。

启动快 21–34%

模型 旧启动 新启动
Qwen3-8B 17.7s 12.5s
Qwen3-32B 30.7s 21.6s
Qwen3-235B 76.1s 50.1s
DeepSeek-V4-Flash 112.2s 77.9s

每副本省 5–34 秒。原因是旧流程在 profiling 阶段要反复分配、释放、再分配整段显存，新流程只挂接实际碰到的页。

块 64 的代价

块大小默认值从 16 升到 64，动机是记账不是速度：块表条目、分配器元数据、前缀哈希都随块数线性增长，块变大四倍，元数据少四倍。ROCm 保持 16。没有 16 对 64 的实测基准。

代价在两处：序列最后一块的未用尾巴被闲置，预期约每序列（块−1）/2 个 token（16 时 7.5 个、64 时 31.5 个）；前缀缓存按整块复用，共享前缀只复用到最后一个完整块边界。200 token 上下文下未用槽位 2.66% 对 10.24%，1000 token 下 0.55% 对 2.24%。短请求上最痛：40 token 提示在块 16 下命中 32 个 token，块 64 下命中 0。短提示、短共享前缀的服务先测命中率再决定默认值去留。

升级注意

保留显式利用率值的四种情况：其他进程共享 GPU、统一内存设备（如 DGX Spark）、RL 式权重更新的权重传输缓冲、自带设备缓冲的 KV 连接器。其余都是估计法定容时代的习惯，可以删。恢复旧行为用 --gpu-memory-utilization 0.9 或 --no-enable-extensible-kv-cache。

上线前核对：同一 GPU 上两个引擎仍需显式份额；晚分配器（边车或第二个任务在热身后抢显存）会与按整卡定容的缓存竞争；显存告警规则要改——健康副本的显存占用会长期贴近满格，改告警 vllm:kv_cache_usage_perc 与抢占次数；固定大小覆盖（kv_cache_memory_bytes 或 num_gpu_blocks_override）会关掉这个功能；同批其他 0.34 破坏性改动包括模型运行器 V1 移除、huggingface_hub 不低于 2.0.0、ROCm 7.2 镜像下线。

TPOT 的取舍：发布说明写明部分 H200 模型在并发 128 时单 token 解码延迟上升 6–18%。机制没有给出，推测是缓存变大后调度器同时跑的序列更多、解码 batch 更大，每步做更多功；高并发下吞吐上升、首 token 延迟下降，每个 token 却稍慢一点。有硬性 TPOT 目标时用 --max-num-seqs 封顶运行集，这个建议未对照 0.34 验证，先用自己的流量做基准。
