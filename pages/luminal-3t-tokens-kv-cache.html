Luminal 推理云扩到每天 3 万亿 token：97% KV 缓存命中率是怎么做到的

  • 原文：How We Scaled Above 2 T Tokens A Month or Why I Did Not Sleep in October（Matthew Gunton，Luminal 博客，2026-11-18）
  • 收藏日期：2026-11-20

一句话要点

Luminal 的推理云几周内从每天几千亿 token 扩到每天 3 万亿以上，靠的不是堆 GPU，而是把 KV 缓存命中率当作第一性原理来守：接纳单位改成“席位”（一段正在进行的会话），故障时把请求打散再迁回，扩容逐节点进行、路由器流量每次只放 10%，峰值日 3120 万请求、3.22 万亿 token，命中率合计 97.3%。

核心数字

  • 规模：峰值日接入 3120 万次请求、3.22 万亿 token（输入+输出）；峰值过后日均 1.67 万亿，工作日峰值 2.6 万亿；可用性 99%。
  • 请求形态：平均约 8.5 万个输入 token，中位提示词 14.6 万 token，p90 27.6 万，最大 55 万；请求体约 2.0 MB；工作日平均每分钟约 9000 个请求，即每分钟 18 GB 请求体、持续 2.5 Gbps。
  • 命中率：集群每小时命中率合计 97.3%；扩容后回到 98%（11 月 3 日）。
  • 经济学：DeepSeek 缓存输入价比未缓存输入便宜 50 倍（每百万 token 非高峰 0.003 美元对 0.15 美元）；16 万 token 的轮次，热轮次输入成本约 0.0005 美元，冷轮次 0.02 到 0.05 美元；命中率掉 1 个点，答案成本大约增加 20%。
  • TTFT：同一会话冷启动 12.6 秒（预填充 16 万 token），热启动 1.45 秒（只预填充 86 个 token）；冷请求来得比集群预填充速度快时，首 token 时间中位数在 0.6 秒到 12 秒之间波动；冷会话每 1000 个 token 约 0.08 秒。
  • 事故：10 月 14 日一次单步流量份额变化移动约 325 个会话，几分钟内命中率掉到 80% 到 91%；10 月 19 日一个客户以批准速率 3.5 倍发送请求；10 月 20 日重试风暴中 06:00 拒绝占比 90%，13:00 当小时尝试约 640 万、拒绝占 74%。

机制一：席位，不是请求

SaaS 通常按请求跟踪，但请求是 KV 缓存的错误度量单位：继续一段已见过的会话只要几千个未缓存 token 的预填充；开启新会话或移到从没见过它的副本上，要花掉整个对话记录（中位数约 14.6 万 token）。请求计数器分不出这两种，而正是第二种会压垮集群。

接纳单位改成席位：一个席位是一段正在进行的会话。路由器维护一本笔记本，记录放在 GPU 上的会话；每次请求按会话 id 查表。持有席位的会话整个生命周期都去同一批 GPU；席位在最后一次轮次后 5 分钟内算占用，该行保留 1 小时。没有席位的会话，只有别名未超上限、且 GPU 当前能接纳时才获得席位；达到上限则本轮被拒绝、不写行，之后可认领空出的席位；GPU 实际没服务过的轮次永远不写席位。

席位的本质是给 KV 缓存逐出一个可控的时钟：时间限制让逐出决策精确，命中率随之提高。备选方案都否了：飞行中请求上限分不出冷热请求；冷请求预算物理上对但路由器在引擎回答前不知道缓存 token 数、只能估算，预测引擎并不比席位近似更好；预热（迁移前先预填充）正在做，但不降性能很难。

机制二：故障转移路由

环形结构先试一个 GPU worker、失败再试下一个，会让后续 GPU 性能大幅下降。做法是把请求分散到整个集群，等新 GPU 恢复在线后再迁回原 worker；流量自然增长也有助于避免 KV 缓存节流。

扩容第一天的教训：放置策略“第一眼看到最空闲的副本就钉住”，让少数副本钉在序列上限、排队 50 到 130 个请求，其他副本闲置；过载副本被看作“崩溃”，不良行为在节点间跳来跳去。修复是两条规则：一、按副本自数飞行中的请求而不是问引擎（避开指标引擎的延迟）；二、设上限（避免在吞吐-交互曲线上滑坡）；同一档内缓存前缀最长的胜出。第二天集群到 98.0%，保持一周。

机制三：首 token 时间保护

冷预填充（可能命中率低的请求）是最重要的技能：短时间内大量冷预填充会让其他请求退化，所以把它们分散到各 worker 是维持 SLA 的真正要求。高命中率让客户花得更少，也帮服务商在 SLA 内服务更多请求，两边利益一致。

负载单位是每分钟冷会话数，所有接纳决策都是为了限制这个数。扩容本身有命中率代价：重新画像的副本重启后是空的，新节点加入时是空的，放置环会把一部分现有会话洗牌到新节点上。代价与移动的会话占比成正比，所以扩容要慢慢来：逐节点走排空、下线、准备、接纳，由单租约做围栏、出错即失败关闭；新状态路由器的流量每 6 分钟只放 10%。

机制四：到 GPU 的网络也是模型的一部分

第一堵墙在路由器：平均请求体 0.8 到 2.0 MB，路由 CPU 的网卡在其核心饱和之前先饱和，出站连接在同一条饱和链路上挨饿。

10 月 19 日的客户超速事件暴露两点：冷预填充比例飙升，要按席位和预期冷预填充 token 数限流；网卡饱和很大程度上由智能体重试策略驱动——返回带 Retry-After 头的 429 时，大多数 OpenAI API 客户端都会照做，固定数值的 Retry-After 会让所有流量同时回来（雷鸣般的 herd）。办法是把 Retry-After 的值打散；客户不一定遵守，最后手段是封禁行为不良的客户。

可复用的结论

  • KV 缓存命中率是推理服务的第一性原理：命中率每掉 1 个点，成本涨约 20%（97% 基线）。
  • 接纳与限流的单位要与成本单位对齐：按请求计数管不住冷预填充，按会话（席位）才能管住；限流要按席位+预期冷预填充 token 数。
  • 扩容的代价是会话移动占比：单步移动 325 个会话就能让命中率几分钟内掉到 80%–91%；正确做法是逐节点、有围栏、流量 10% 每 6 分钟。
  • 故障转移不要用“试下一个”：打散再迁回；放置决策要自数在途请求、设上限、同档取最长前缀。
  • Retry-After 必须是打散的值，固定值会制造重试风暴；网卡先于 CPU 核心饱和，网络是模型的一部分。
