Humming 接入 SGLang：量化表示与执行路径分离，低比特 MoE 核

  • 原文：Humming in SGLang: Flexible Low-Bit Kernels for Efficient MoE Serving（LMSYS 博客，2026-11-18 发表）
  • 作者：蚂蚁集团 Venus 与 SCT 团队、SGLang 团队
  • 主题：低精度量化（MXFP4/FP8）、GPU kernel、推理优化、MoE、SGLang
  • 星级：⭐⭐⭐⭐（重点阅读）
  • 一句话要点：Humming 把量化数据的表示与执行策略分开，检查点保留紧凑表示，运行时按设备与负载选兼容的计算路径；DeepSeek-V4.1-Flash-1017 上，相同 A16 精度下相对 Marlin 预填充提速 1.07 至 1.23 倍，FP8 专家激活再降路由 GEMM 时间约 47.6%。

核心结论

Humming 是轻量、即时编译的核库，面向量化稠密与 MoE 推理；0.1.18 版把 SGLang 集成扩展到更多量化方案与 GPU 架构。DeepSeek-V4.1-Flash-1017 上，相同 A16 精度下相对 Marlin 取得 1.07 至 1.23 倍预填充提速，FP8 专家激活作为独立部署选项单独评测，附带精度与投机解码接受率结果。

关键设计是把量化数据的表示与执行策略分开：检查点保留紧凑表示，运行时按设备与负载选兼容的计算路径。预填充与解码可以对同一份检查点用不同的执行策略；加载时准备一次，推理时按层组合输入处理与 GEMM。

表示与执行分离

MoE 推理同时面对两处挑战：专家权重存储大，分给每个专家的 token 数一直在变。4 比特权重省存储与内存流量，但高效服务还需要合适的反量化、Tensor Core 指令与足够的并行工作。

Humming 让兼容的格式共享数据搬运、反量化、矩阵乘法与输出处理组件；支持稠密与 MoE GEMM、低比特整数与浮点权重、多种激活精度。具体组合能不能用，取决于 GPU、scale 格式与张量布局，带版本的配置指南定义了这些约定。

模型加载时，Humming 把支持的检查点张量与元数据转成通用的权重与输入 schema。填充、转置、交错与 scale 重排在请求热路径之外准备好张量。

三层配置把职责分开：LayerConfig 描述形状、数值格式、量化与存储布局；ComputeConfig 描述稠密、索引或分组执行与累加语义；TuningConfig 选择 tile 形状、数据传输、流水线级数与调度。兼容的计算选择可以复用已准备好的权重；改存储布局或目标架构就要重新准备。

推理时，统一的 process_input 接口处理兼容的激活求值、Hadamard 变换、布局处理与量化组合。输入量化包括静态张量 scale、动态逐 token 或逐组 scale，以及支持的二级 scale 组合；选中的操作取决于层，有的 scale 计算要跑多遍。Humming 随后组合并即时编译选中的 GEMM，设备与形状相关的选择平衡并行度、权重复用与流水线深度，编译产物缓存起来供后续调用。0.1.18 版打磨了这些选择，包括 MoE 调度与权重逐出，这样不用为每种格式与服务形状预编译全部组合。

Hopper：MXFP4 存、FP8 算

Hopper 上有代表性的一条路径是 MXFP4 权重配逐 token FP8 激活。权重在全局与共享内存里保持 4 比特打包；Humming 在 Tensor Core 计算之前才重建 FP8 操作数。

这条路径分三步。第一步，加载时分解 scale：概念上，每个 UE8M0 组 scale 分解为 s_g = s_base × 2^Δg。这条路径为每个专家与子层保留一个基 scale，另为每组留一个残差指数码；编码包含重建所需的偏移量。指数跨度超过 FP8 支持范围时，准备阶段调整并重新量化受影响的 FP4 值。

第二步，寄存器内重建 FP8 权重：FP4 半字节与残差指数在矩阵乘法之前拼成 FP8 E4M3 操作数。转置映射把权重寄存器放进 WGMMA 的 A 操作数、把共享内存里的激活 tile 放进 B 操作数，内存里不物化 8 比特权重张量。

第三步，尾声应用剩余 scale：FP8 WGMMA 累加进 FP32。尾声应用激活 scale 与分解后的基 scale；残差指数已经合进权重操作数。

举例：四个组 scale [1, 2, 4, 8]，基 scale s_base=1，残差指数 [0, 1, 2, 3]。scale 为 4 的组里 FP4 值 1.5 重建成 E4M3 操作数 0.1875；剩余权重因子是 32，恢复 0.1875 × 32 = 6 = 1.5 × 4。这些值包含固定的 FP4 到 FP8 指数偏置调整；激活 scale 单独应用。

E4M3 下这条路径支持的指数跨度是 11，不用调整 scale 范围。跨度更大时，最小 scale 升到 max_scale / 2^11；受影响组里的权重除以对应的 2 的幂再舍回 FP4，可能引入舍入误差或下溢。0.1.18 版在 TP8/EP1 下的加载时检查发现，scale 范围调整出现在 0% 的有效目标组与 11.27% 的有效草稿组，主要是填充的 scale 影响了草稿的范围选择。填充导致的这个问题已在上游修复，将在后续的 Humming 依赖升级里合入。

融合 E8M0 配置把准备与执行连起来。其他 scale 布局用各自对应的核与准备规则。0.1.18 版还改进了 FP8_BLOCK 分组连续与索引 MoE 路径；这些路径用块 scale 激活，下面的 AFP8 结果用动态逐 token E4M3 scale（组大小为 0），不度量这些块 scale 路径。

Blackwell：新增原生计算路径

全部实测结果都在 Hopper H20-3e 上；Blackwell 一节讲架构支持。Humming 的架构通过 BF16 UMMA 与符合条件的 FP8、FP4 与 INT8 UMMA 路径扩展到 Blackwell。支持的 SM10x 配置可以用 UMMA，支持的 SM12x 块 scale 配置用 MXMMA。

这些是设备与格式相关的选择。INT8 UMMA 不是每块 Blackwell 设备都有，scale 布局必须与选中的指令路径匹配。同一套配置框架在处理这些约束的同时，也为不同服务形状选择 tile 与流水线。

接入 SGLang

最初的集成把 Humming 接进 SGLang，更新到 0.1.18 的集成随后合入。SGLang 掌管专家路由、分发、token 对齐、输出归约与 token 顺序；Humming 提供兼容的输入处理与 GEMM 执行。

量化加载与专家执行是相关但不同的职责。SGLang 可以对兼容的量化线性层用 Humming，也可以选它的 MoE runner，同时为稠密层保留另一条原生路径。SGLang 读检查点元数据，保留选中方案所需的输入 scale。选 Humming 不会自动把 A16 激活转成 FP8，静态量化仍需要校准过的 scale。

提议的更新把门控 MoE 激活经可选的 activation_type 与 activation_impl 字段接进 process_input。调用方指定拆分或交错的门控/上行输入，并给出激活的 CUDA 表达式；内置的 SiLU、截断 SiLU、基于 erf 的 GELU 与 SiTU 共享这个接口。下行投影因此可以通过同一条输入处理路径表达兼容的激活求值、Hadamard 变换与量化。实现保留 BF16/FP16 舍入边界，激活与量化能合并时不产生不必要的中间激活缓冲。这个接口让模型专用的激活复用同一条输入处理路径。

Humming 支持 DeepSeek-V4-Flash、DeepSeek-V4-Pro（含 V4-Pro-0813）与 DeepSeek-V4.1-Flash 的原生 MXFP4 专家执行。提议的共享输入处理接口还覆盖 GLM-5.2/5.3 与 Kimi-K2.x/K3 的门控激活路径；Kimi-K3 支持包括从仍在评审的适配改来的原生 MXFP4 加载桥。另一处提议的修复让标准 EP 分发按每 rank 的路由工作估计 GEMM 调优，同时完整计入复制的共享专家，下面的 Humming EP8 实测包含这处修复。

端到端结果只覆盖 DeepSeek-V4.1-Flash-1017。兼容的专家并行部署也可以用 DeepEP FP8 分发，把量化激活与 scale 带进 Humming。

在 SGLang 里用 Humming

Humming 0.1.18 的基础支持已合入 SGLang。下面的基准还包含提议的输入处理集成，Humming EP8 配置应用了 EP 调优修复。报告的环境固定 Humming 0.1.18；0.1.19 未对这些结果做验证。

按 CUDA 大版本装对应的编译器扩展：CUDA 13 装 humming-kernels[cu13]==0.1.18，CUDA 12 装 humming-kernels[cu12]==0.1.18。

--moe-runner-backend humming 在检查点的原生量化路径支持 Humming 时选专家执行；--quantization humming 为兼容的线性层与专家层选 Humming 的模型级量化适配器。兼容的 MoE 模型用这个适配器时，两个都要选。保留检查点的原生稠密层路径、同时在 Humming 专家里显式用 FP8 E4M3 激活时，设环境变量 SGLANG_HUMMING_INPUT_QUANT_CONFIG='{"dtype":"float8e4m3"}' 再启动服务。用投机解码时，也为草稿选 --speculative-moe-runner-backend humming。用 {"dtype":"bfloat16"} 显式选 BF16 激活。只加后端标志不会要求 FP8 激活。

Humming 还支持加载时从未量化的 FP16/BF16 检查点做在线权重量化：SGLANG_HUMMING_ONLINE_QUANT_CONFIG='{"dtype":"float4e2m1","group_size":32,"scale_dtype":"float8e8m0"}' 要求 MXFP4 权重（32 元素组、UE8M0 scale）配 FP8 激活。权重 schema 接受 dtype、group_size 与 scale_dtype；SGLang 还支持 ignored_layers，让选中的层不转换。对已量化的检查点，在线转换要在权重配置里显式加 "force_requant":true。这些设置只选加载行为，不为静态激活量化提供校准过的 scale。

下面的结果用已有的原生 FP8 稠密/MXFP4 专家检查点，显式选激活，不用在线权重量化。

读懂实测结果

预填充画像把后端效应与激活精度选择分开。相同 A16 精度下，Humming 的路由专家 GEMM 累计核时间比 Marlin 少 31.6% 至 32.4%，覆盖 4K、128K 与 1016K。Humming 内选 AFP8 再把 GEMM 时间降约 47.6%。

1016K 下，其余 GPU 核在三种配置里都约 151 秒。这解释了为什么路由 GEMM 时间的减少只换来较小的端到端预填充提速。其余部分包括注意力、稠密/共享专家工作、路由、激活与通信，不是只测注意力。

并发为 1 时，A16 轨迹里 Humming 路由 GEMM 每次目标验证为 3.77 毫秒，Marlin 为 4.21 毫秒；草稿 GEMM 为 0.195 毫秒对 0.181 毫秒。两者都用 M=8 的 MoE tile。

解码延迟与接受率：值是三次运行的均值 ± 样本标准差。首 token 时间含排队；每输出 token 时间度量首 token 之后每输出一个 token 的时间。接受率是每次验证步的平均输出 token 数，对请求取平均。估计解码毫秒/步是每次运行内 1000 × Σ（端到端 − 首 token 时间）/ Σ（验证步数）。验证步数由输出长度除以接受率恢复。这把周期成本与每周期产出的 token 数分开，同时包含草稿、验证、调度与传输，不是 GPU 核时间。

EP1 下保留的完整 GSM8K 评测得分：Marlin A16 为 97.12%，Humming A16 为 97.04%，Humming AFP8 为 96.82%。定向 RULER v1 检索检查里，Marlin A16 与 Humming AFP8 在名义 32K 与 128K 下各得 200/200。这些结果只描述评测过的配置，不证明一般精度等价，也不证明 1016K 性能点的质量。

基准细节与复现

测试用 CUDA 13.0、Humming 0.1.18 与 FlashInfer 0.7.2，跑在 8 块 H20-3e GPU 上。检查点是 DeepSeek-V4.1-Flash-1017，含自带的 DSpark 草稿。全部列用含输入处理集成的 SGLang 版本；Humming AFP8 EP8 额外应用了 EP 调优修复的运行时改动。目标与草稿用同一 MoE 后端；这些运行不设 --quantization humming。Humming 用索引 GEMM 与动态逐 token FP8 scale 做 AFP8；FlashInfer 的 FP8 激活路径由 --flashinfer-mxfp4-moe-precision fp8 选中。

服务启动用 TP8、EP 可配、预填充 CP 交错、DSpark 块大小 5、--mem-fraction-static 0.84、--chunked-prefill-size 16384 等参数；客户端用 sglang.benchmark.serving，预填充测 128K 输入、32 输出 token、并发 1，解码用 ShareGPT、4096 输入 token、1024 生成 token，并发 1/32/64 分别用 10/160/320 个实测请求，热身与测量各跑三遍。

GSM8K 得分用全部 1319 道测试题、8 样本提示；RULER 检查用 niah_multikey_2，Marlin A16 与 Humming AFP8 各在 32K 与 128K 下跑 200 个例子。两者都用温度 0 与 thinking=false。这些保留的精度结果覆盖所述的 EP1 配置。

下一步

Humming 计划引入自动调参，在目标设备上跑候选配置，为每个负载找到更好的执行参数，补上现有的启发式规则。后续硬件支持包括 Rubin Locality Domains、T-Head 的 Zhenwu M890 与更多 CUDA 兼容加速器，按各自的计算与内存特性适配核。

SGLang 集成方面，基于统一输入处理支持更多原生量化检查点与自定义激活，同时减少权重加载时的填充、重打包与峰值内存；改进 EP 感知的调优、量化 DeepEP 分发与动态专家迁移，把端到端覆盖扩展到这些路径与 B300 部署。

启示

这篇的通用教训是：量化推理的收益不在“换更低精度”本身，而在表示与执行分开之后、每条路径都能按设备与负载专门化。Hopper 上 MXFP4 存、FP8 算的收益来自三处：权重 4 比特常驻省搬运，寄存器内重建省物化，指数分解让 scale 融进操作数与尾声；SGLang 侧只接管路由与调度，量化执行交给兼容的核。

读实测要分清两个变量：后端效应与精度选择。相同 A16 精度下，Humming 相对 Marlin 的预填充提速 1.07 至 1.23 倍是后端效应；AFP8 再降约 47.6% 的 GEMM 时间是精度选择，代价是 GSM8K 从 97.12% 降到 96.82%。1016K 下其余核约 151 秒不动，说明长上下文预填充的瓶颈不在路由 GEMM，换核只能收走其中一部分。
