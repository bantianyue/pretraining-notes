一句话要点

JAX 加 Transformer Engine 把 DeepSeek-V3 671B 训练从 103 提到 1068 TFLOPS/GPU，提升 10.4 倍：分组 GEMM 处理不规则专家形状，专家并行整合派发与合并，MXFP8 分组量化压低专家矩阵乘法成本；1024 块 GPU 上扩展效率 97%。

核心数字

  • 未优化基线：103 TFLOPS/GPU，通信占累计内核时间的 84%（DeepSeek-V3，GB300）
  • 优化后：1068 TFLOPS/GPU，提升 10.4 倍；端到端吞吐提升约 10 倍
  • 四档优化的 TFLOPs/GPU/秒：105 → 425 → 730 → 1025；tokens/GPU/秒：418 → 1693 → 2907 → 4082
  • 多机架扩展：128/256/512/1024 卡，TFLOPs/GPU/秒 1025/1025/1010/990，扩展效率 100%/100%/99%/97%
  • 从 128 卡扩到 1024 卡，单卡算力只从 1025 降到 990，降幅约 3.4%

MoE 训练的瓶颈

  • 生产规模的 MoE 训练会冒出稠密模型没有的瓶颈：token 路由、专家派发与收集、all-to-all 通信、不规则专家 GEMM
  • 路由器是学习到的：训练中路由器逐渐偏好某些专家，没有两个批次的专家负载是相同的；同一个批次里，一个专家可能收到很多 token，另一个只收到很少
  • 每个专家收到的 token 数不同，拼不出规整的矩形 GEMM，只能得到不规则张量；多数库针对均匀、矩形的张量做了高度优化
  • 专家并行下，token 必须派发出去，输出必须合并并恢复原始 token 顺序；派发与合并路径不优化，通信就会占主导、GPU 空转

无丢弃与容量受限的取舍

  • 无丢弃 MoE：每个 token 都会被选中的专家处理，不管负载多不均匀；对模型质量有吸引力，对系统要求很高
  • MegaBlocks 把专家计算重构成块稀疏矩阵乘法，让每个专家处理不同数量的 token，既不丢弃也不填充；需要新的块稀疏 GPU 内核、优化的分组 GEMM、派发与合并原语
  • 容量受限 MoE：每个专家分到固定 token 预算，超出的要么裁掉、要么填充补齐到固定预算；计算规整、硬件友好，但要在模型质量与效率之间直接取舍
  • 丢掉溢出 token，模型只能在不完整的数据上训练；填充避免丢弃，训练就要白白付出算力与显存
  • 选了无丢弃路线，训练栈就不能再依赖固定的专家形状；token 数是数据决定的、CPU 上拿不到，内核还要在 CPU 拿不到形状的情况下工作，才能用 CUDA 图、避免重编译

三项核心优化

  • 组感知的 MXFP8 量化
  • 专家矩阵乘法上的 MXFP8 分组 GEMM
  • 派发与合并的优化专家并行操作
  • 一层跨两块 GPU 的专家并行 MoE 层：路由器给每个 token 分配专家，派发把 token 送到专家所在的 GPU，分组 MLP 在可变长度的组上跑两轮分组 GEMM，合并反向交换、恢复原始 token 顺序

优化一：分组 GEMM

  • 稠密前馈网络里每个 token 走同一个权重矩阵；MoE 里路由器把 token 不均匀地分给专家，每步每个专家收到的 token 数不同，常规 GEMM 依赖的规整形状被打破
  • 此前的办法是循环调用 GEMM 内核与批量 GEMM：循环需要把 token 数从设备拷回主机，走在关键路径上，带来设备到主机传输的延迟，还会打断 CUDA 图；批量 GEMM 按最坏情况的 token 容量算，哪怕实际用的 token 更少，也要填充到固定专家计算量，多算很多
  • 分组 GEMM 用一次内核调用处理全部专家矩阵乘法，每个专家按实际 token 数算；只算有有效 token 的区域，性能因此更高
  • Transformer Engine 的 grouped_gemm / ragged_dot 用 cuBLAS 与 cuBLASLt 做后端，直接映射到性能最好的 NVIDIA GEMM 库，即使专家形状不规则也能吃满 Tensor Core
  • Blackwell GPU 上这条路还打开了专家矩阵乘法的 MXFP8 块缩放，用的是 Transformer Engine 的分组量化内核

优化二：专家并行整合派发与合并

  • 派发：token 移动发生的地方：token 重排并跨 GPU 发送，涉及本地重排与多 GPU 通信
  • 合并：处理过的 token 送回原始 GPU，各专家结果累加
  • 简单实现里这两个阶段串行跑：一串独立操作，GPU 在步骤之间停顿，数据多次读写内存，通信在计算跑的时候基本空闲，反过来也一样
  • Transformer Engine 的专家并行实现把派发与合并整合成一条紧密集成的融合内核路径，动力来自 NCCL EP，一个专门针对专家并行路由产生的不规则、不均衡流量调优的通信后端
  • NCCL EP 还有 token 去重机制：一个 token 派发到同一 rank 上的多个专家、或远程 IB 节点上的多个 rank 时，只在网络上走一次，到达节点后再复制，节省网络带宽
  • 专家并行与分组 GEMM 互补：分组 GEMM 管专家内部发生什么，专家并行管专家周围的一切

另外两项优化

  • JAX 主机卸载：中间激活不必整个前向都存在设备上；JAX 提供重物化 API，把激活卸载到主机内存；DeepSeek-V3 训练里为了省显存，把查询与值投影的结果卸载到主机
  • XLA 多流集合通信：默认 XLA 在单流上跑通信，能并行执行的集合操作被串行化，有的还暴露在关键路径上；多流集合通信让编译器把独立的集合操作调度到不同的 CUDA 流上并发执行，跨节点 InfiniBand 传输与节点内 NVLink 通信重叠
  • 延迟隐藏调度器（LHS）分析集合操作的副本组、检查死锁风险，决定哪些集合操作可以安全重叠；内存带宽收益自动产生，不用手动标注
  • 这项优化把 DeepSeek-V3 训练里暴露在关键路径上的集合操作占比大幅压低

上手：复现配置

  • 优化随 NVIDIA NGC MaxText 容器发布，Transformer Engine 已经内置；容器用 2026 年 9 月 10 日（ghcr.io/nvidia/jax:maxtext-2026-09-10）或更新的版本
  • 打开 TE MoEBlock 的六项配置：te_moe_block: true、te_gmm_quantization: "te_mxfp8"、ragged_buffer_factor: 2.0、te_ep_overflow_check_every_n_steps: 20、sparse_matmul: true、prefuse_moe_weights: true
  • 复现 DeepSeek-V3 671B 的配置：model_name deepseek3-671b、max_target_length 4096、per_device_batch_size 6、gradient_accumulation_steps 1、steps 15、attention cudnn_flash_te；quantization te_fp8_currentscaling；weight_dtype 与 mu_dtype 均为 bfloat16；128 卡配置为总 FSDP=16（ICI 8 × DCN 2）× EP=8，nodes 32
  • XLA 标志：all_reduce 组合阈值 33554432 字节、all_gather 6442450944 字节、reduce_scatter 201326592 字节；command_buffer 开 FUSION、CUBLAS、CUDNN、DYNAMIC_SLICE_FUSION；max_unroll_factor 8、memory_limit_slop_factor 99
  • 环境变量：XLA_PYTHON_CLIENT_MEM_FRACTION 0.88、CUDA_DEVICE_MAX_CONNECTIONS 16、XLA_PJRT_GPU_HOST_MEMORY_PREALLOCATE false、XLA_PJRT_GPU_HOST_MEMORY_LIMIT_GB 180
  • 先用参考配置，在小 MoE 模型上验证正确性，再扩规模；跟踪步时间、TFLOPS/GPU、MFU、分组 GEMM 延迟、MoE 派发与合并延迟

与 4-bit 训练篇的关系

  • 4-bit 训练篇（Inkling 2 Small）解决的是数值格式问题：NVFP4 前向、MXFP8 反向、随机舍入、RHT 加 S2F6 通信
  • 这篇解决的是 MoE 结构问题：不规则形状、派发合并、专家并行；两篇的交集在 MXFP8：这里用 MXFP8 分组量化做专家矩阵乘法，那里用 MXFP8 做反向
  • 两篇都落在 GB300 NVL72 上，数字可以对照：NVFP4 在 GB300 上 15 PFLOPS、每值 4.5 比特；这里的分组 GEMM 路径在 Blackwell 上打开 MXFP8 块缩放
  • 下一步计划：NVFP4、与 GEMM 融合的量化、A2A 重叠——正是 4-bit 训练篇已经验证过的方向

值得注意的细节
