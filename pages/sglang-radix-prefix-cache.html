SGLang Radix 前缀缓存上 TPU：Qwen2.5-7B 吞吐涨 63%，混合模型上却拖后腿

原文：https://kitrakrev.github.io/projects/sglang-tpu-agent-serving/（Karthik Raja Anandan，2026-11-18，SGLang on Cloud TPU v6e） 星级：4 星 | 收藏日期：2026-11-21 | 主题：KV 缓存、推理优化、TPU、并行策略（推理）

一句话要点

多轮 Agent 每轮重发同一份长系统提示加不断变长的历史，服务速度取决于前缀缓存复用。SGLang 的 radix 前缀缓存在 TPU v6e-1 上把 Qwen2.5-7B 从 930 推到 1,515 输出 token/s（c=32），TTFT p99 从 598 毫秒降到 134 毫秒，命中率 84–88%，全部请求落在 200 毫秒 SLO 内。同一面旗子在混合线性注意力模型上反噬：Qwen3.8-27B 开缓存后每个并发都更慢。

核心结论

  • 缓存让 TTFT 尾部压平：v6e-1 上 Qwen2.5-7B，c=32 时吞吐 930 → 1,515 token/s，TTFT p99 598 → 134 ms，命中率 84–88%，100% 请求在 200 ms SLO 内。
  • 混合线性注意力上缓存反噬：Qwen3.8-27B 开缓存处处更慢：快照只落在 1,024 token 边界，命中率 32–38%，最大运行请求从 96 掉到 27。
  • H100 快 1.65–2 倍，TPU 赢在尾延迟：c=32 时 H100 2,502 token/s 对 v6e-1 的 1,515；A100 与 v6e-1 大致打平，但 v6e-1 的 TTFT p99 是 134 ms 对 410 ms。

Run A：前缀缓存在 Qwen2.5-7B 上

c=32 时吞吐 930 → 1,515 tok/s、TTFT p99 598 → 134 ms、命中率 84–88%。c=96 见顶 2,755 tok/s（按需约 $0.27/1M token）。c=128 时 KV 驱逐、命中率 88% → 75%、TTFT p50 涨 10 倍。解码是 HBM-bound：下限 15.2 GB / 1.64 TB/s = 9.3 ms，实测 ITL 12.9 ms（73% roofline）/ 19.8 ms（55%）。

Run B：缓存反拖后腿

Qwen3.8-27B（48 层 Gated-DeltaNet + 16 层全注意力）开缓存处处更慢：命中率 32–38%，最大运行请求 96 → 27，ITL 在 c=1 时 12.0 → 26.7 ms。根因是快照只落在 1,024 token 边界，循环状态检查点太贵，缓存复用省下的 prefill 抵不过快照与驱逐的代价。

Run C：int8 权重与 OLMo 移植

int8 仅权重：c=32 时 1,505 → 2,342 tok/s、ITL 20.1 → 12.9 ms、KV 池 232k → 345k token，无精度评测。OLMo 2/3 prefill 慢 10–30 倍（32 KV 头、fallback 查询块 2 vs 32）。

三卡对比：按 HBM 字节算其实一样

卡 c=32 吞吐 TTFT p99 结论
v6e-1 1,515 tok/s 134 ms 尾延迟最好
H100 2,502 tok/s — 快 1.65–2 倍
A100 与 v6e-1 大致打平 410 ms 尾延迟差 3 倍

三卡 c=1 时均约 73% roofline；H100 的差距主因是带宽（3.35 vs 1.64 TB/s），不是软件。

结论

前缀缓存不是通用加速开关：它跳过的是 prefill 的 FLOPs，不是 decode 的 KV 读取，所以 TTFT 能压 4.5 倍、ITL 几乎不动；它在纯注意力模型上值 63%，在混合线性注意力模型上要先有更便宜的循环状态检查点才划算。报数要报 SLO 内的 goodput。
