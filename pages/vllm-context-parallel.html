vLLM 上下文并行部署（Context Parallel Deployment）· 中文精读

原文：https://docs.vllm.ai/en/latest/serving/context_parallel_deployment/（vLLM 官方文档） 精读日期：2026-09-30 ｜ 主题：并行策略（推理）

0. 为什么 prefill 和 decode 要分开做 CP

长上下文服务的核心矛盾：prefill 和 decode 的特征与 SLO 完全不同，所以上下文并行要分开设计：

  • 长上下文 prefill：目标是控制 TTFT（首 token 延迟）——把 prefill 的计算量摊到 query token 上；
  • 长上下文 decode：目标是腾出更多 KV cache 空间——装下更大 batch，换吞吐。

1. Prefill CP

长请求有 T 个新 token，要算这 T 个 token 的 Q/K/V。N 卡就把请求切成 N 个 chunk，每卡算一个 chunk 的 Q/K/V。两种策略：

  1. 部分 query + 全量 key/value：请求中等长度、放得下全量 K/V 时用。把各卡的 K/V gather 起来，每卡算自己 chunk 的 query 对应的 attention 输出。目标是加速 prefill。
  2. 部分 query + 部分 key/value：请求太长、全量 K/V 放不下。每卡只算自己 chunk 的 Q/K/V，用 ring-attention 逐块 send/recv K/V。

两种都在积极开发中。

2. Decode CP：核心是切分 KV cache

decode 是自回归：每步只有少量 query token，要 attend 海量存在 paged KV cache 里的 key/value。decode CP 的核心问题就是KV cache 怎么分片。

H 个 kv-head、T 个 token 的上下文 → KV cache 存 H×T 个 key/value 张量。三种情况：

  1. 单卡放得下且性能够 → 不并行；
  2. 放不下 / 想多装请求 → 先沿 H 维度切，就是普通张量并行（-tp <num_gpus>）；
  3. H 有限（模型结构决定），TP 继续放大时，每卡的 KV cache 会被复制 tp_size / H 次 → 再加 decode CP，沿 T 维度继续切（-dcp <size>）。

关键细节：

  • -dcp 不增加启动的 GPU 数量，只是减少 KV cache 复制；
  • dcp 取值范围 [1, tp_size/H]：越大复制越少，但通信开销越大；
  • 理论上 dcp 可以超过 tp_size/H，但 decode 的 query token 太少，多出来的卡在 non-attention 层没事干，所以上限就是 tp_size/H；
  • KV cache 在 decode 过程中会增长，用 interleaving（交错）策略沿 T 切分，让未来的 token 自然落到分片上（Moonshot 的 Chao Hong 提出）。

实战 case

  • DeepSeek-R1（开 MLA 时 1 个 kv-head）：单节点 -tp 8 → 8 倍 KV cache 复制，加 -dcp 8 消除；
  • Kimi-K2（架构类似 R1，参数更多）：-tp 16 → 16 倍复制，-dcp 16 完全消除（通信代价更高），或 -dcp 8 降到 2 倍复制（DCP 通信只在节点内，开销小）；
  • Qwen3-235B-A22B（4 个 kv-head）：-tp 8 → 2 倍复制，-dcp 2 消除。

经验法则：先把 -tp 加到性能满意，再加 -dcp 消复制。支持 MLA 和 GQA 模型，部分 attention 后端还支持 DCP + MTP（多 token 预测）组合加速 decode。

3. 与训练侧 CP 的对照

训练 CP（Ring Attention） 推理 decode CP
切分对象 attention 的 Q/K/V 计算（沿序列） KV cache 存储（沿 T 维度）
通信模式 K/V 块在环上轮转，计算与通信 overlap 切分 KV cache，减少 TP 引入的复制
优化目标 显存：放下超长序列的训练 延迟+利用率：多装请求、降复制

同一思想（沿 sequence 维度切），目标不同：训练为吞吐+显存，推理为延迟+KV cache 利用率。

4. 相关指标

cache_config.effective_attention_block_size 上报含 DCP 的有效 attention block 大小（token 数），如物理块 16 token、DCP=4 时代表 64 token。可通过 gRPC Control.GetServerInfo 获取。
