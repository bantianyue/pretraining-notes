一句话要点

Baseten 为 DeepSeek-V4.1-Flash 从零写了一个 Rust 与 CUDA 推理引擎：DSpark 三层 MTP 草稿一次起草多个候选 token，秩 256 的 Markov 校正补上 token 间的依赖，目标模型一次前向验证整块；8 卡 B300 上 2060 TPS，平均每步 2.71ms、每步产出约 5.6 个 token。

核心数字

  • 8×B300（TP8）：2060 TPS，平均步进 2.71ms；4×GB300（TP4）：1740 TPS，平均步进 3.30ms
  • 每步平均产出：2060 × 0.00271 ≈ 5.58 token/步；每 token 平均约 0.485ms
  • 百万 token 预填充约 12 秒（独立结果，不是解码速率的测试条件）
  • 目标模型：40 层、隐藏维度 5120；每层路由 MoE 有 384 个专家，每个 token 选 6 个；专家中间维度 2304
  • 注意力：64 个头、头维度 512；滑动窗口 128 个 token；主 KV 来源层是 2、8、14、20（从 0 计数）；稀疏注意力选择 top-k 512
  • DSpark 草稿模型：3 层 MTP、128 个专家、top-3 路由；Markov 校正秩 256；词表 129280
  • 一个路由专家权重：Pₑ = 3dh = 3 × 5120 × 2304 = 35,389,440；40 层 × 384 个专家总量 543,581,798,400
  • 解码示例生成一个俄罗斯方块游戏的 HTML，复现请求里关闭了思考；温度与 top-p 固定为 1

架构：因果编码器-解码器加稀疏 MoE

  • DeepSeek-V4.1-Flash 是因果编码器-解码器模型：前 20 层是编码器，后 20 层是解码器；解码器用编码器提供的上下文，候选池给后面的稀疏索引层供料
  • 架构里还有混合专家（MoE）层，以及用于投机解码的草稿模型 DSpark；模型说明里提到共享全局 KV、稀疏索引、有界滑动窗口回放与 Engram 条件查找记忆，这些都会影响处理长提示词时要做多少工作
  • 一个目标 token 每层只选 6 个专家：路由专家权重总量虽大，实际激活的只是其中一小部分；这正是 MoE 推理的算术——权重总量不是成本，激活量才是

接受长度怎么算

  • 普通解码里，主模型生成一个 token，再用这个 token 生成下一个；投机解码加一个更小的草稿模型，提前提议几个 token，主模型（目标模型）再把这些提议一起检查
  • 引擎提交一段草稿前缀，再加一个额外 token；如果选中的前缀在草稿结束前就断了，额外 token 会替换掉下一个草稿 token；如果 4 个草稿 token 全被接受，目标模型也算出了 D 之后那个位置的分布，可以再从中采样一个 token
  • 请求日志把每步平均输出 token 数叫做平均接受长度：接受的草稿 token 数除以步数，再加 1 token/步；接受长度 5.6 token/步，意思是平均每步约 4.6 个被接受的草稿 token，加 1 个额外 token
  • 即使一个草稿 token 都没被接受，这一步仍然会产出一个替换 token；一步产出的 token 在流式输出时也可以一起到达，平均每 token 0.485ms 不等于每 0.485ms 就到达一个 token

DSpark 三层草稿加 Markov 校正

  • 解码循环里三个主要调用：dspark_draft() 起草 token，verify_prep(...) 准备验证，spec_accept 提交结果；引擎先起草 token，再用目标模型检查，最后提交结果
  • DSpark 三层 MTP 草稿一次起草 6 个候选，目标模型一次验证 7 个位置；秩 256 的 Markov 校正补上 token 间的依赖——草稿 token 之间不是独立的，校正让一次起草的多个候选在联合分布上更可信
  • 速度来自几处机制合力：DSpark 三层 MTP 草稿、Markov 校正、FP8/FP4 低精度权重、CUDA 图捕获、低 token 数 MoE 链与层间通信融合；编码器-解码器结构又让百万 token 预填充的层-token 评估接近减半

2060 TPS 这个结果能说明多少

  • 这是相当程度的特化：引擎特化到一个模型、一小段 token 区间与 Blackwell 画像，温度与 top-p 固定为 1；FP8 验证头与近似 prefill 回放都不是等价性承诺
  • 没有同条件对照测量，2060 TPS 建立不了 Baseten 比匹配的 SGLang 或 vLLM 部署快多少，也建立不了结果在其他提示词与负载下如何泛化；这些问题需要在相同条件下测量
  • 公告里的汇总数本身就是近似值：用 5.6 除以步进时间算出来约 2066 TPS（2.71ms）与约 1697 TPS（3.30ms），接近但不完全等于标题速率 2060 与 1740 TPS
  • 研究对象是以下快照，而不是假设一个持续变动的主分支永远表现一致：Baseten DeepSeek Ultrafast 76766a97308bfd1658fb055e835d0f92de737dc3；SGLang a56dbcf181cfb7f395c340a093ec5a0bca22cae5；vLLM（针对性代码检查）9bc16ae6a34b1e0fe260e8d12b98568478bf38c3；DeepSeek 模型仓库 314113f8a7dadb388215396ba5fbee2c610a04d6

值得注意的细节

  • TP4 与 TP8 的意思是，一次模型执行用张量并行分布在 4 卡或 8 卡上；这些 GPU 是在一同服务一个请求，而不是 4 份或 8 份独立副本各自跑出这个速率
  • 两处配置都用 Blackwell Ultra GPU：HGX B300 服务器把 8 卡接到 x86 CPU 上，GB300 NVL72 机柜把 72 卡接到 NVIDIA Grace CPU 上，两者都用 NVLink 连接 GPU；Baseten 的"4×GB300"结果用的是 GB300 系统里的 4 卡，不是整个机柜
  • README 的百万 token 预填充是另一项独立结果，不能据此认定俄罗斯方块解码速率是在百万 token 上下文里测到的
  • 计算与作图脚本用 Python、NumPy 与 Matplotlib 复现分析示例与图表；字节数一律按十进制 GB/TB，除非另有说明；逻辑流量、分配的打包存储与实测硬件传输是分开算的
