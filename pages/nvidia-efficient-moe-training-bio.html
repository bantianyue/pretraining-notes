原文：Efficient MoE Training for Biological Foundation Models（NVIDIA Technical Blog，2026-09-24 发表，2026-10-15 更新） 收藏：2026-11-06，星级 4⭐（重点阅读：MoE 训练实战配方） 主题：并行策略（训练）/ MoE 架构 / Kernel 优化 / 低精度量化（MXFP8）/ 专家并行

一句话要点

MoE 只激活少数专家，容量与算力解耦；NVIDIA Transformer Engine 用 GroupedLinear 分组提交、MXFP8 块缩放、低精度融合 kernel 三件套收掉专家切碎、显存、量化转换三处开销，BioNeMo 配方在 8 张 B200 上把 Mixtral-8x7B 训练吞吐量做到 Hugging Face 基线的 2.21 倍。

背景：MoE 的账怎么算

稠密 Transformer 里每个 token 都要走过每一层，模型能力加一点，训练和推理的计算就多一点。MoE 换了扩展方式：模型里放很多专家子网络（subnetworks），每个 token 只路由给其中少数几个。参数总量可以很大，单个 token 实际花的计算却很小。容量与单 token 计算解耦，是 MoE 的核心红利。

但红利不是免费的，好处能不能拿到手看实现：

  • 专家计算被切碎：朴素实现逐个跑专家，内核启动和调度开销随专家数线性增长，GPU 利用率掉下来。
  • 路由带来通信开销：token 要分发到不同专家、结果再汇总。
  • 参数 footprint 变大：分布式训练的显存压力跟着上来，基因组任务又经常用长序列，激活显存压力更大。

NVIDIA Transformer Engine（TE）针对这三处给优化原语：分组专家计算（grouped expert computation）、kernel 融合（kernel fusion）、低精度训练（low-precision training）。生物基础模型的参数量和序列长度都在涨，这些原语既能提 GPU 效率，又能把模型容量再往上扩。BioNeMo 的 MoE 配方把它们落成可直接跑的参考实现。

挑战一：专家计算被切碎，内核启动太多

MoE 把单个稠密前馈模块换成多个专家网络。Hugging Face 的基线实现在 Python 循环里逐个遍历专家，每个专家触发一次单独的内核启动：

for expert_idx, expert_layer in enumerate(self.experts):
    idx, top_x = torch.where(expert_mask[expert_idx])
    current_state = hidden_states[None, top_x].reshape(-1, hidden_dim)
    current_hidden = expert_layer(current_state) * routing_weights[top_x, idx, None]
    final_hidden_states.index_add_(0, top_x, current_hidden)

时间随专家数线性增长。分组执行保留每个专家各自的权重矩阵，但把它们的工作一起提交。TE 的 GroupedLinear 把多个线性变换收进一次调用：收集专家权重和输入 token，因为每个专家分到的 token 数不一样，调用时额外传一个每专家 token 数的参数 split_sizes，本地专家走 TE 的分组 GEMM 路径，而不是每个专家单独调一次 PyTorch Linear：

from transformer_engine.pytorch.ops import GroupedLinear

experts_gate_up = GroupedLinear(
    num_groups=num_local_experts,
    in_features=hidden_size,
    out_features=2 * intermediate_size,
    bias=False,
    dtype=torch.bfloat16,
    device="cuda",
)
gate_up_output = experts_gate_up(tokens, split_sizes)

关键点：

  • 分组 GEMM 的收益在启动与调度开销，不是算力本身。8 个专家一次提交，时间由最慢的那个专家决定，而不是 8 次启动累加。
  • Hugging Face Transformers 也有 grouped_mm，但 TE 的差异在融合：GroupedLinear 能和 MXFP8 量化、激活、路由权重缩放、中间数据搬运进一步融进 GroupedMLP kernel（挑战三）。

挑战二：模型变大，显存吃紧

BF16 每个权重和激活值占 16 位。BioNeMo 配方用 TE 支持 FP8 和 MXFP8 训练，两种格式都只用 8 位，显存占用直接减半。

FP8 和 MXFP8 的差别在缩放粒度：

  • FP8：张量级或通道级缩放，动态范围受限。
  • MXFP8：每 32 个连续值配一个共享缩放因子（E8M0 格式），更好地保留数值范围和精度。
  • 在 Blackwell GPU 上，MXFP8 是硬件加速的，MXFP8 GEMM 能用专门的 Tensor Core 指令。

这与 Hopper FP8 MMA 的精度机制是同一条线：低精度训练的核心矛盾永远是数值范围与精度的 trade-off，块缩放把缩放粒度从张量级压到 32 个值一块，是目前最实用的折中。

挑战三：量化与反量化白白多跑几步

训练计算大多用 8 位精度，但模型的主权重保留在 16 位。框架因此要在两种格式之间来回转换：量化把 BF16 权重和激活转成 MXFP8 再进低精度 GEMM，反量化把结果转回高精度格式。朴素路径把这些步骤当成独立操作各跑一遍。

解法分两步：

第一步，MXFP8 配方 + autocast。 把 MXFP8BlockScaling 配方挂到模型上，用 TE autocast API 给前向和反向打开 MXFP8 精度：

fp8_recipe = te_recipe.MXFP8BlockScaling()
model = TEMixtralMXFP8ForCausalLM(config, fp8_recipe=fp8_recipe, dispatcher=dispatcher)

with te.autocast(enabled=True, recipe=self._fp8_recipe):
    for decoder_layer in self.layers:
        hidden_states = decoder_layer(hidden_states)

第二步，Sequential API 融合 MLP。 导入 TE 的 Sequential API，把 gate_up、ScaledSwiGLU、down 串起来，API 还把反量化折进融合路径。ScaledSwiGLU 把路由概率（scales）和专家前馈网络的计算合在一起：

from transformer_engine.pytorch.ops import GroupedLinear, ScaledSwiGLU, Sequential

experts_ffn = Sequential(GroupedLinear(gate_up), ScaledSwiGLU(), GroupedLinear(down))

TE Sequential API 扫描这些操作，模式匹配上就把 GroupedLinear → ScaledSwiGLU → GroupedLinear 这一串替换成一个融合操作对象：前向是 ForwardGroupedMLP_CuTeGEMMSwiGLU_MXFP8，反向有对应的融合操作。三重收益：减少框架开销；SwiGLU 和概率缩放的工作融进分组 MLP 路径；避免物化一部分中间结果。

融合的逻辑与 FlashAttention 的思路同构：把多次 HBM 往返压成一次 kernel 内完成，中间结果不落内存。

实测：8 卡 B200 上提速 2.21 倍

Mixtral-8x7B，8 张 NVIDIA B200 Tensor Core GPU：

配置 吞吐量（tokens/s/GPU）
Hugging Face BF16 + FSDP8 4,096
Transformer Engine BF16 + FSDP8 4,447
Transformer Engine 专家并行 + MXFP8 9,050

9,050 / 4,096 = 2.21 倍。注意分解：只换 TE 不换精度（BF16）是 4,447 / 4,096 = 1.09 倍；专家并行 + MXFP8 再带来约 2.04 倍。精度与并行的收益是乘法关系，不是加法。

跑起来：两卡验证，八卡全量

先用两卡的 L0_sanity 配置跑通，确认专家并行和训练环境都没问题：

torchrun --nproc_per_node=2 train_fsdp2_ep.py --config-name L0_sanity

验证通过后上 Mixtral-8x7B 配置，专家并行 EP=8，MXFP8 精度，8 张卡：

torchrun --nproc_per_node=8 train_fsdp2_ep.py --config-name L1_8x7B_ep checkpoint.ckpt_dir=/path/to/ckpt

工程要点：BF16 还是 MXFP8，按 GPU 和显存需求选；数据并行和专家并行的规模要配好，两者乘积等于总 GPU 数；融合 MXFP8 GroupedMLP kernel 必须用 Blackwell GPU。配方 README 里有启动、检查点和基准测试的完整命令。

与知识库其他条目的联系

  • Hopper FP8 MMA 内幕（4⭐）：低精度训练的精度机制——截断、舍入、累加器提升。MXFP8 的块缩放是同一问题的工程解：把缩放粒度压到 32 个值，既保精度又保硬件效率。
  • MoE 架构（主题）：专家并行、负载均衡、稀疏模型的设计与训练。GroupedLinear 是 EP 的计算原语。
  • Prime Mega MoE（素材池）：DeepSeek 融合 MoE 内核补上可重叠反向传播，端到端训练快 1.34 倍。同一赛道的不同打法：TE 融合 MLP vs Prime 的反向重叠。
  • Together Compiler（5⭐）：持续编译的思路与 TE 的融合 kernel 形成对照——一个是编译期把算子融好，一个是运行期让智能体持续重写前向。
  • torchtitan 年度更新（5⭐）：FSDP2 是这篇配方里 train_fsdp2_ep.py 的并行底座，EP 与 FSDP2 的组合是当前 MoE 训练的标准并行形态。

关键数字备忘

  • MXFP8：每 32 个连续值共享一个 E8M0 缩放因子；8 位 vs BF16 16 位。
  • Mixtral-8x7B，8×B200：HF BF16 FSDP8 4,096 → TE BF16 FSDP8 4,447 → TE EP8 MXFP8 9,050 tokens/s/GPU，最高 2.21 倍。
  • 融合 kernel：ForwardGroupedMLP_CuTeGEMMSwiGLU_MXFP8（前向），反向有对应融合操作。
  • 门槛：专家并行至少 2 卡；融合 MXFP8 GroupedMLP 必须 Blackwell。
