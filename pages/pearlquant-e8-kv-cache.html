PearlQuant：E8 格量化 KV 缓存，128 并发下首 token 从 144 秒降到 7 秒（中文精读）

  • 原文：PearlQuant: KV cache quantization for production-scale LLM serving，Pearl Research Labs，2026-11
  • 原文链接：https://pearlresearch.ai/research/blog/pearlquant
  • 收藏日期：2026-11-14
  • 星级：4⭐
  • 主题：KV 缓存 / 低精度量化 / 推理服务

一句话要点

E8 格量化把 KV 缓存压到每值 3.2 比特：8 个值一组、240 个面，比 FP8 的立方体多装信息；128 并发下首 token 从 144 秒降到 7 秒，吞吐高 24%。

为什么 KV 缓存是瓶颈

  • GLM-5.3 有 78 层，每 token 每层 576 个值；10 万 token 的会话，FP8 KV 缓存要 5.1 GB，PearlQuant 只要 1.8 GB。
  • 长上下文服务里，KV 缓存不在 GPU 上就得从 CPU 的 LMCache 里拉：128 个并发会话下，FP8 的 p90 首 token 要 144 秒，PearlQuant 7 秒。
  • 每值比特数：FP8 基线 9.1 比特（含 scale 开销），PearlQuant-3.2 只要 3.2 比特，每值省 65% 存储。

E8 格：为什么 8 个值一组

  • 标量量化把每个值独立量化，浪费在"立方体"的角上：FP8 的立方体只有 16 个面，E8 格有 240 个面，同样比特数装更多信息。
  • 8 个值一组、用 E8 格的 240 个面编码：浪费比特数 PearlQuant 0.39 / 0.42，TurboQuant 0.56 / 0.60，NVFP4 1.15，FP8 2.65。
  • 2D / 3D / 8D 格量化分别比标量省 13% / 19% / 47% 存储；维度越高，格越密。
  • 解码在片上完成：Blackwell CuTe DSL 解码内核，格解码不用走 HBM round-trip。

精度：3.2 比特几乎无损，2.1 比特掉长上下文

  • KL 散度（PG-19，FP8 约 0.04 是噪声地板）：PearlQuant-3.2 0.057，2.3 是 0.122，2.1 是 0.207。
  • 基准：RULER 97.2 / 97.1 / 96.5 / 94.8，LongBench v2 69.2 / 68.2 / 69.0 / 60.4，MMLU-Pro 86.3 / 86.1 / 85.5 / 85.7，LiveCodeBench 95.7 / 94.9 / 93.6 / 95.2——3.2 比特与 FP8 无显著差别，2.1 比特在长上下文上掉。
  • "Wait" 测试（每 1000 词多等的词数）：3.2 比特 −1% / +2% / +3%，2.1 比特 +77% / +106% / +48%。
  • 自评判：3.2 比特被判更好占 53.2%（随机是 50%），2.1 比特 69.7%（置信区间 66–73%），FP8 对 FP8 是 52.5%。

服务实测

  • 8 张 B200、vLLM + LMCache、DP=8，AgentX 真实 Claude Code 轨迹：128 并发会话下 p90 首 token FP8 144 秒 → PearlQuant 7 秒。
  • 峰值吞吐比 FP8 高 24%；轻负载下 FP8 反而领先约 8%（量化解码有固定开销，小批量摊不薄）。
  • 结论：KV 缓存量化不是单纯省显存，是把"从 CPU 拉 KV"的等待时间换成"片上解码"的计算时间；并发越高，赚得越多。

结语

  • 格量化的收益随维度放大：8 维 E8 格是甜点——240 个面、每值 3.2 比特、精度几乎无损；再往下压到 2.1 比特，长上下文先掉。
  • 这套打法与具体模型无关：只要 KV 缓存是瓶颈、且能接受片上解码的固定开销，格量化就能把首 token 时间从分钟级拉回秒级。
