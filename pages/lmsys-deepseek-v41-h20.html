LMSYS DeepSeek-V4.1-Flash H20：八处改动，端到端延迟降 65.5%，吞吐涨 2.91 倍

原文：https://www.lmsys.org/blog/2026-11-19-deepseek-v41-h20（LMSYS Blog） 星级：4 星 | 收藏日期：2026-11-21 | 主题：并行策略（推理）、PD 分离、低精度量化、推理优化

一句话要点

DeepSeek-V4.1-Flash 在 8 卡 H20-3e 上用 SGLang 的 PD 分离部署跑 64K 输入时，Prefill 先排队：基线 TP4 下平均端到端 13.63 秒、首 token 12.04 秒。七处改动之后，平均端到端降到 4.70 秒（降 65.5%），输出吞吐从 847 涨到 2,465 token/s（2.91 倍）；其中 Prefill 交错 CP 加 Decode DP 一步降 44.64%，FP8 DeepGEMM 打分再降 29.85%。

核心结论

  • Prefill CP 加 Decode DP 是最大头：一步端到端降 44.64%。Prefill 用交错 CP 把长请求 token 行分到 4 卡，Decode 用 DP 把不同请求分到 4 卡；首 token 从 12.04 秒降下来。
  • FP8 DeepGEMM 打分再降三成：Indexer 打分改 FP8 E4M3，64K 探针里 1,677 万个采样键值无一需截断，与 BF16 打分共享 99.08% 的 top-k 选择；端到端再降 29.85%。
  • 同卡部署每卡吞吐更高：单机 4 卡同卡部署端到端从 18.62 秒降到 7.96 秒，每卡 371 token/s 高于 PD 分离的 308；代价是每 token 时间从 3.20 涨到 5.62 毫秒。

评测口径

256 个请求、24 并发、61,440 共享前缀 + 4,096 token 增量、500 token 输出、10 次热身后 flush 缓存，缓存命中 93.21%。七处改动分工清楚：并行方式改的是 Prefill 与 Decode 各自的切分，FP8 打分与分块放大改的是 Indexer 的算量与复用，选择融合与 K 块复用改的是验证路径的重复劳动，可打断 CUDA Graph 改的是长 Prefill 的核启动。每一处都有独立的服务基准对照，百分比按相邻行算，不能跨行相加。

八处改动

招数 改动
第 1 招 Prefill 交错 CP，Decode 用 DP
第 2 招 Prefill Indexer 改 FP8 DeepGEMM 打分
第 3 招 可打断 CUDA Graph 管 Prefill
第 4 招 MoE 从专家并行改张量并行
第 5 招 Indexer 打分块放大到 2 GiB
第 6 招 Prefill 选择与写回融合成一个核
第 7 招 验证时复用分页 Indexer K 块
第 8 招 同卡部署再进一步

累计效果与同卡部署

阶段 平均端到端 输出吞吐
TP4 基线 13,633.80 ms 846.76 tok/s
七处改动后 4,698.65 ms 2,464.90 tok/s

同卡部署（单机 4 卡）：端到端从 18,619.53 ms 降到 7,957.13 ms，每卡 371 token/s，高于 PD 分离的 308 token/s。代价是每 token 时间 3.20 涨到 5.62 ms。
