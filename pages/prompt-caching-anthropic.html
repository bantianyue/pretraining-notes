Anthropic Prompt Caching：缓存命中只付 0.1 倍 token 价 —— 中文精读

原文：What is Prompt Caching in LLMs?（aiengg.dev，Gaurav Sen，2026-10-13） 星级：⭐⭐⭐⭐ 重点阅读｜主题：推理优化、KV Cache、API 成本 收藏日期：2026-10-14｜一句话：Anthropic 的提示缓存把已处理过的前缀存下来复用，命中只付 0.1 倍价；能不能命中全看提示布局——静态置顶、参数垫底，前缀逐字一致才能复用。

1. 问题：重复的提示，每次都在全价重算

调用大模型的 API 时，提示里的大部分内容和上一次一模一样：工具定义、系统指令很少变，用户的问题也常常只是换了几个空。但模型每次都要把整个提示重新读一遍，每一个 token 都要付费。

根源在自注意力：语言模型用自注意力读提示，把序列中不同位置两两关联。单层自注意力的代价是 O(n²·d)（n 为序列长度，d 为 token 表示维度），长度翻一倍，该层做四倍的功。重复读 = 重复付平方级代价。

2. 机制：前缀匹配，逐字一致

Anthropic 的解法是提示缓存（prompt caching）：API 把之前调用中处理过的内容保留，只完整处理新增部分。对从缓存读到的输入 token，按 0.1 倍基准输入价计费。

复用只有一个条件：前缀匹配。API 把每次请求开头的一段（prefix）与最近处理过的内容比对，要求逐字一致——前缀里任何一处改动，都会让它之后的内容全部重算。Anthropic 按固定顺序组装前缀：工具 → 系统 → 消息。工具定义和系统指令天然稳定，所以能对上。

3. 布局：静态置顶，参数垫底

能不能命中，取决于提示怎么写：

  • 填空式（string replace）：答案写进正文中间的空里。第一个答案（邮箱）紧跟第一个问题，前缀到它就结束——六个问题里五个在它后面，每次都要重算，大部分内容白付全价。
  • 答案放底部：六个问题固定，答案统一写在最后一个问题之后。前缀一口气穿过工具、系统和全部问题，只有答案是新增工作量。

Anthropic 文档的要求也是后者：静态内容放提示开头。

4. 成本账本：写入 1.25 倍，5 分钟窗口

  • 写入 5 分钟缓存：收 1.25 倍基准输入价。
  • 有效期默认 5 分钟，每次命中刷新计时。
  • 太短的提示不进缓存：最低门槛 512–4096 token，视模型而定。
  • 账很好算：多花的 0.25 倍写入费，第二次调用就回本；之后每次读六个固定问题只付一折。

5. 边界：模型专属，不要中途换模型

提示缓存是模型专属的。Claude Code 团队 2026 年 4 月的例子：和 Opus 聊了 10 万 token 后，换 Haiku 答一道简单题反而更贵——Haiku 没有这些 token 的缓存，要从头重建。切换模型 = 下一次请求零命中重读整个对话。团队的建议是用子代理：由 Opus 为另一个模型准备交接消息。

6. 与 KV Cache 的关系

提示缓存本质上是 KV cache 的跨请求复用：前缀的 K/V 已经算好存在服务端，新请求只算增量部分的注意力（新 token 对全部前缀的 attention）。这与推理引擎里的前缀缓存（prefix caching，如 vLLM/SGLang 的自动前缀复用）是同一思想在 API 层的产品化——区别在于 API 层要求调用方主动按"静态置顶"布局，而推理引擎多为自动匹配。

7. 落到实战的三条约束

  1. 逐字匹配：模板渲染时注意空白、顺序、工具定义的序列化稳定性，任何抖动都杀死命中。
  2. 5 分钟窗口：低频调用享受不到；高频 agent 循环、批量任务是主要受益者。
  3. 模型专属：路由/降级策略要在"便宜模型"和"缓存命中"之间算总账，10 万 token 上下文下切模型几乎总是亏。
