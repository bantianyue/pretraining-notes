LLM 服务引擎解剖：vLLM 与 SGLang 的五层进程切分

LLM 服务引擎解剖：vLLM 与 SGLang 的五层进程切分 — 中文精读

原文：Anatomy of an LLM Serving Engine（Aditya Kumar，hiraditya.github.io，2026-10-28 发表，2026-11-01 更新） 收藏：2026-11-06，星级 5⭐（核心必读：推理引擎架构） 主题：并行策略（推理）/ 推理优化 / KV Cache / 训练推理一致性 版本：vLLM 0.32.0（提交 5df63a7）、SGLang 0.5.22（提交 baa9bef）；十篇系列第 1 篇

一句话要点

每个 LLM 服务引擎都是同样的五层（API 前端、调度器、KV 内存管理、模型执行器、集群层），vLLM 与 SGLang 的差别不在有哪几层，而在把这几层切成几个操作系统进程、以及哪个进程拥有内存；vLLM 引擎核心独掌 KV 账本、Worker 只存字节，SGLang 每个张量并行 rank 各跑一份完整引擎、靠确定性保持账本一致。

五层模型：按决策与状态划分

一层值得单独命名，当且仅当它拥有一个决策，以及这个决策需要的状态：

层 决定什么 拥有什么
L1 API 前端 一个请求是哪串 token ID，输出 token 变成什么文本 对话模板、分词器、每个请求的反分词状态、停用字符串
L2 调度器 哪些 token 进下一次前向 等待与运行队列、每步的 token 预算
L3 KV 内存管理 每个 token 的键值住在哪 块或槽位表、空闲链表、前缀索引
L4 模型执行器 怎样在 L3 分配的槽位上，对 L2 挑出的批次跑一次前向 权重、KV 字节、CUDA 图、编译好的 kernel
L5 集群层 哪个副本接这个请求 每个副本的负载与缓存命中估计

两个关键结构关系：

  • L2 与 L3 拆不开。 接纳一个请求就是内存决策（调度器在赌这个请求后面需要的块到时候还空着）；抢占就是把赌注撤回。PagedAttention 让赌注变得便宜（KV 按需分配成固定大小的块）。在一个引擎内部，L2 和 L3 永远坐在一起，两个引擎都把它们放进同一个进程。
  • L5 住在引擎外面（vLLM 的 llm-d、SGLang 的 Rust Model Gateway），但它需要知道 L3 知道的事，所以两个引擎都把 KV 状态往上导出，这个导出就是集群层伸回引擎的地方。

小引擎验证：nano-vllm（1,195 行非空非注释 Python，README 称约 1,200 行）有 Scheduler、带哈希前缀缓存的 BlockManager、ModelRunner、在自己进程里做分词与反分词的 LLMEngine，没有 HTTP 服务器与集群层（离线引擎）；Mini-SGLang（5,972 行，README 称约 5,000 行）把前端放在自己的进程里，调度器和执行器按每卡一个进程放在一起。作者不同，规模差 5 倍，引擎里面还是同样的四个盒子。

总图：两卡下的进程切分

系列每篇都以这张总图开头，并标出该篇覆盖的框。每个框是一个进程，按双卡张量并行画出（两个引擎看起来不一样的最小配置）。

  • vLLM：引擎核心每步都把批次发给 Worker（共享内存广播）。
  • SGLang：rank 0 只把新请求发给 rank 1，每个 rank 自己算出批次。

把五层切成操作系统进程不是表面包装。在 Python 与 CUDA 运行时里，一道进程边界同时是三道边界：GIL 边界、地址空间边界（指针传递变成序列化或共享内存拷贝）、权限边界（两张 GPU 是由一个控制器指挥，还是各自独立算出完全相同的调度）。

vLLM：引擎核心管账本，Worker 管显存

默认单 API 服务器时，vllm serve 进程就是 API 服务器；AsyncLLM 把引擎核心作为子进程启动（EngineCore）。引擎核心的忙循环可以写成一行：排空输入队列，然后 step() 依次跑 scheduler.schedule()、model_executor.execute_model()、scheduler.update_from_output()。

Worker 数量：文档与代码说法不一致。 架构总览说每个 GPU 一个 Worker 进程，总数是 A + DP + N。但 ParallelConfig 在 world_size == 1 时选 uni 执行后端，UniProcExecutor 把 Worker 建在引擎核心进程里面——单卡 vllm serve 是两个进程，不是三个。到 -tp 2 时后端变成 mp，MultiprocExecutor 派生出 VllmWorker-0 与 VllmWorker-1，数量跳到四个。

基准测试陷阱：TP=1 时 vLLM 的调度器和前向共享地址空间与 GIL，跟 SGLang 的布局一样；TP=2 时不再一样。传 -tp 2 改的是引擎的进程拓扑，不只是张量并行。单卡上采的 CPU 画像完全测不到加第二张卡才出现的引擎到 Worker 的 IPC 路径。

TP≥2 时，一个请求去 GPU 的路上要跨两道进程边界，两跳用的传输方式不一样：

  • API 服务器 → 引擎核心：ZMQ ROUTER/DEALER 套接字收请求，PUSH/PULL 套接字回输出，线上传 msgspec 打包的 msgpack；引擎核心用两个专用后台线程跑套接字 I/O 再喂给 queue.Queue（释放 GIL，能把 ZMQ I/O 与 GPU 重叠，还能把部分序列化/反序列化与模型前向重叠）。
  • 引擎核心 → Worker：shm_broadcast.py 里的 MessageQueue，共享内存环形缓冲，每 Worker 一个写者一个读者；引擎核心每步写一次 SchedulerOutput，所有 Worker 读同一份字节；每个 Worker 在自己的一对一队列上回包，只有一个 rank 返回 execute_model 的结果。

KV 初始化四步（EngineCore._initialize_kv_caches）：

  1. 问每个 Worker：每个注意力层每 token 需要什么（全注意力、滑动窗口、MLA、Mamba 状态……），得 kv_cache_specs。
  2. 每个 Worker 用 dummy 前向画像，报剩给 KV 的字节：ceil(total * gpu_memory_utilization) - 非 KV 内存 - CUDA 图估计（集合 RPC，-tp 2 时结果是每 Worker 一项的列表）。
  3. 字节在这里变成块，就在引擎核心里；每个 rank 都按最小 rank 的块数裁，块 ID 4711 在所有 GPU 上指同一个槽位。
  4. 只有这时 Worker 才分配：每 GPU 一块 int8 缓冲，按层看成 KV 张量；之后再跑 torch.compile 与 CUDA 图捕获。

第 4 步之后，Worker 再也不做内存决策。引擎核心里的 BlockPool 拿着空闲块队列和前缀缓存查询的块哈希表；每步调度器把块 ID 随 SchedulerOutput 发下去（新请求走 NewRequestData.block_ids，长过块边界的走 CachedRequestData.new_block_ids）；模型执行器按 ID 指向的地方写键值。Worker 拥有内存，引擎核心决定内存的含义。

进程边界的两个后果：

  • KVConnector 在引擎到 Worker 的边界上劈开。 跨解耦引擎搬 KV，既要知道传哪些逻辑块（EngineCore 里的 L3 状态），又要知道 GPU 内存指针在哪（Worker 里的 L4 状态）。TP=1 之后没有单个进程同时有这两样，所以 vLLM 按角色把接口劈开（KVConnectorRole.SCHEDULER 与 KVConnectorRole.WORKER），两半每步通过 SchedulerOutput.kv_connector_metadata 对话；TP=1 时劈法也成立，两半共享 EngineCore 进程。
  • 停用字符串在前端到引擎的边界上付往返延迟。 停用 token 便宜（EngineCore 在采样结束时立刻看到 token ID，自己就能结束请求）；停用字符串定义在文本上，只有 API 服务器里的 OutputProcessor 有文本，匹配到时 EngineCore 还不知道，还捏着请求的块，还可能在 abort 经 ZMQ 到达之前又调度一步。高并发部署里，模型词表允许时优先用停用 token。

SGLang：每个张量并行 rank 跑完整引擎

启动器在主进程里启动 TokenizerManager（连同 HTTP 服务器），每个张量并行 rank 一个 Scheduler 子进程，再加一个 DetokenizerManager 子进程。--tp-size 1 是三个进程，--tp-size 2 是四个（--dp-size 2 再加一个 DataParallelController 父进程）。

Scheduler 在进程内建出 Worker：Scheduler → TpModelWorker → ModelRunner。L2、L3、L4 在每张 GPU 上共享一个进程，选批次、分配 KV 槽位、启动 CUDA kernel 之间没有任何东西跨进程边界。

回报是 CPU-GPU 重叠变成 local state。 Scheduler.event_loop_overlap 在计算流上启动第 N 批，同时在 CPU 上处理第 N-1 批的结果，而第 N 批正在 GPU 上跑；机制就是两条 CUDA 流加一个进程内 future 映射，不是序列化边界。vLLM 0.32 用默认调度器 AsyncScheduler 拿到类似的重叠，但 TP=1 之后必须跨共享内存环形缓冲做流水线。

代价是状态复制。 每个 rank 的 Scheduler.__init__ 都建自己的 ReqToTokenPool、TokenToKVPoolAllocator、一份 RadixCache 前缀树。只有 rank 0 经 ZMQ 从前端收请求；请求到达时 rank 0 调用 broadcast_pyobj（pickle 成字节张量，经 Gloo CPU 组做 dist.broadcast）。入口广播之后，每步不再发批次；每个 rank 在本地的队列与基数树副本上跑同样的调度代码，靠确定性得出完全相同的批次与槽位分配。rank_consensus_checker 可以验证这一点，但只有打开 SGLANG_ENABLE_RANK_CONSENSUS_CHECKER 时才启用，默认是个空操作。

确定性赌注的脆弱点：一个遍历请求 ID 字符串集合的决胜逻辑就足以打破它——SGLang 用 spawn 方法启动调度器，每个都是全新的解释器，除非钉住 PYTHONHASHSEED，否则 CPython 会给每个解释器随机化字符串哈希；任何读墙钟的策略都有同样的问题。哪边都不会报错：各 rank 在集合操作里挂起，或者每个 rank 的注意力头悄悄从另一个请求那里读键。

反分词放在自己的进程 DetokenizerManager 里（源码没给理由，按代码的读法：调度器进程处在 kernel 启动的关键路径上，每个请求的解码状态与 batch_decode 调用放在里面会拖慢下一次启动；单独的进程把字符串工作从调度循环与 HTTP 事件循环上都挪开）。vLLM 同样的工作放在 API 服务器的事件循环上，分块跑，中间插 await asyncio.sleep(0)，让大输出批次不至于饿死其他请求。

内存定容陷阱：两个引擎都按各 rank 里最差的那张 GPU 给 KV 池定容，但两个开关量的分母不一样：

  • vLLM 的 --gpu-memory-utilization 是 vLLM 分配的一切的总上限；KV 拿到的是扣掉权重、画像出的激活、CUDA 图估计之后剩下的部分。
  • SGLang 的 --mem-fraction-static 是只针对静态内存（权重加 KV 池）的目标份额；其余部分留作运行时 slack，slack_gb = pre_model_load_memory * (1 - mem_fraction_static)，KV 池拿到的是模型加载后剩下的空闲内存再扣掉这份 slack。

同一台机器上把两个开关都设成 0.9，得不到同样的 KV 池。

谁拥有内存：两种答案

vLLM 0.32 SGLang 0.5.22
TP=1 / TP=2 时的进程数 2 / 4 3 / 4
TP=2 时的调度器份数 1 份，在引擎核心里 2 份，每 rank 一份
TP=2 时的 KV 账本份数 1 份 2 份，靠确定性保持相同
KV 字节住在哪 每个 Worker 进程 每个调度器进程
各 rank 怎样对齐批次 引擎核心每步把 SchedulerOutput 写进共享内存 rank 0 广播新请求，各 rank 自己调度
反分词 API 服务器事件循环 单独的进程
内存开关 --gpu-memory-utilization，总上限 --mem-fraction-static，静态份额

vLLM 在 TP 大于 1 之后每步都要付序列化与一次共享内存跳转，调度器永远碰不到 GPU 张量；SGLang 为 N 份调度器付 CPU 时间，还把正确性押在 N 个进程做出比特完全相同的决策上。

作者更倾向 vLLM 的切法：KV 账本有一个单一权威 owner（每个数据并行 rank 一个），这个 owner 也是告诉集群路由器缓存了什么的天然位置——BlockPool 把 BlockStored 与 BlockRemoved 事件排队，打开 --kv-events-config 后 Scheduler.update_from_output 在 ZMQ PUB 套接字上发布它们。一个账本、一个事件流、一个供 llm-d 订阅的来源。SGLang 的单进程循环在单节点上更容易做快；vLLM 的切法在集群层开始问问题时更容易讲清楚。

一个请求的时间花在哪

低负载下（一次只飞一个请求，服务器在两次请求之间空闲），不用给 vLLM 打补丁就能测进程边界开销。vLLM 在 vllm/v1/metrics/stats.py 里的 Prometheus 直方图暴露了足够多的内部时间戳：

  • vllm:request_queue_time_seconds：第一个 SCHEDULED 减 QUEUED（引擎核心单调时间戳）。
  • vllm:request_prefill_time_seconds：首 token 减第一个 SCHEDULED。
  • vllm:request_decode_time_seconds：末 token 减首 token。
  • vllm:request_inference_time_seconds：末 token 减第一个 SCHEDULED（等于预填充加解码）。
  • vllm:e2e_request_latency_seconds：前端挂钟时间，从 arrival_time（对话模板渲染开始时打戳，在分词之前）到前端从 ZMQ 取出最终输出批次的那一刻。

两个解读细节：

  1. 抢占藏在推理时间里，不在排队时间里。 代码只保留第一个 SCHEDULED 事件（带一句 # ignore preemptions 注释），而文档写的是最近一次 SCHEDULED。一个请求生成中途被抢占、重新进等待队列再恢复，第二次等待算进预填充或解码，不算排队时间。
  2. e2e 在最终反分词与 HTTP 写回之前就停表。 e2e 在前端从引擎核心取出最终批次时就停表，排除了最后一次 IncrementalDetokenizer 处理与写 HTTP 响应。

Prometheus 直方图把多个请求的观测聚合在一起，一次抓取报不出单个请求的延迟；但一次只飞一个请求时，每次直方图 _sum 在两次抓取之间的增量就是那个请求的精确观测，_count 的增量说明恰好落了一个观测。完整脚本是 split_latency.py，核心是两次 /metrics 抓取的差分：

# 1. Prove exactly one observation landed in every histogram between scrapes.
for m in HISTOGRAMS.values():
    assert after[m, "_count"] - before[m, "_count"] == 1
d = {k: after[m, "_sum"] - before[m, "_sum"] for k, m in HISTOGRAMS.items()}

# 2. Input tokenization, msgpack + ZMQ both ways, and up to one step waiting
#    for EngineCore's busy loop to drain its input queue.
frontend_ipc = d["e2e"] - d["queue"] - d["inference"]

# 3. HTTP request parsing before rendering, final detokenization, response write, socket.
http_detok = client_s - d["e2e"]

可检验的预测：只有提示词进来的路与最终 token 出去的路坐在 frontend_ipc 里面，之前每个 token 都经 ZMQ 穿过去、在 API 服务器事件循环上反分词，而此时引擎核心已经在 GPU 上跑下一个前向。并发为 1 时，frontend_ipc 在输出长度从 1 长到 256 个 token 时应该保持平坦，只随提示词长度略微增长（分词 2,048 个 token 比 128 个花的时间长）。如果 frontend_ipc 随输出长度增长，说明前端的 asyncio 事件循环在并发为 1 时也跟不上引擎的解码步伐。

最接近的已发表拆分是 vLLM 自己对 Llama 3 8B 在一块 H100 上的画像：HTTP API 服务器占执行时间的 33%、调度占 29%、GPU 执行占 38%。这个画像就是 v0.6.0 把 API 服务器挪进自己进程的原因（它早于上面描述的布局，对今天的残差什么也没说；但它说明前端的份额大到值得单独给一个进程）。

前端是最会动的一层

两个仓库最近的工作给出了干净的检验：两个引擎现在都发实验性 Rust 前端，而且朝相反的方向建。

  • vLLM 的 vllm-frontend-rs（从 Inferact 搬进主仓库）：把北向服务层用 Rust 重建，同时仍然经 ZMQ、在已有的引擎边界上与核心 Python vLLM 引擎进程对话；架构图里的每个 crate 都映射到 L1（axum HTTP 服务器、带推理与工具解析的对话模板渲染、分词器与增量反分词器、ZMQ 加 MessagePack 的引擎客户端，VLLM_USE_RUST_FRONTEND=1）。进程边界留在原地，变的只是 ZMQ 套接字之上的语言。
  • SGLang 用 Rust 删掉了进程边界：打开 SGLANG_RUST_SERVER=1 后，嵌在 rank-0 调度器里的 Rust 服务器拥有 API 服务器、分词与反分词；按调度器源码的说法，Rust 服务器就是入口来源，请求接收器从进程内环形缓冲取数据，而不是走 ZMQ 套接字。L1 与 L2、L3、L4 合并进同一个操作系统进程，Python 的 TokenizerManager 与反分词子进程根本不启动。
  • Model Gateway 在 gRPC 模式下把 L1 往反方向拉，拉进 L5：gRPC 路由器在本地分词输入、支持工具调用解析、流式返回响应。

看两个开关，SGLang 0.5.22 的 L1 可以跑在主进程里、rank-0 调度器进程里，或者网关里，每个地方用不同的实现。层的活与状态从没变过，变的是哪些层跟它共享地址空间、请求在关键路径上付几次 IPC。这就是每个引擎正在做的架构决策，也是这个系列接下来要跟的轴线。

与知识库其他条目的联系

  • Together Compiler（5⭐）：持续编译的思路与服务引擎的进程切分形成对照——一个是编译期把算子融好，一个是运行期让智能体持续重写前向；两者都围绕"谁拥有状态、谁做决策"展开。
  • NVIDIA 生物基础模型高效 MoE 训练（4⭐）：GroupedLinear 与 MXFP8 是训练侧的 kernel 优化；这篇是推理侧的引擎架构，KV 账本与专家并行在训练与推理两侧是同一批概念的不同落点。
  • vLLM 上下文并行部署（4⭐）：prefill CP 与 decode CP 的设计；这篇的进程切分决定了 CP/EP 这些并行策略在推理引擎里由谁执行。
  • Kernel Optimization — Modular 手册（4⭐）：kernel fusion 把 HBM 往返从 6 次降到 2 次；服务引擎的进程边界与 IPC 开销是同一笔账在系统层的版本。
  • Prime Mega MoE（素材池）：DeepSeek 融合 MoE 内核；MoE 推理的 kernel 与服务引擎的调度、KV 管理是上下游关系。

关键数字备忘

  • 进程数：vLLM TP=1 是 2 个、TP=2 是 4 个；SGLang TP=1 是 3 个、TP=2 是 4 个。
  • 教学实现规模：nano-vllm 1,195 行；Mini-SGLang 5,972 行。
  • vLLM 画像（Llama 3 8B，单 H100）：HTTP API 服务器 33%、调度 29%、GPU 执行 38%。
  • 内存开关：vLLM --gpu-memory-utilization 是总上限；SGLang --mem-fraction-static 是静态份额；都设 0.9 得不到同样的 KV 池。
