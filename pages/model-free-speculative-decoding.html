一句话要点

投机解码不用训练草稿模型：Prompt Lookup 从当前上下文复制，REST 从离线数据仓库取，SuffixDecoding 复用系统自己的历史输出，Lookahead Decoding 用目标模型自己的预测拼 n-gram；目标模型一次验证定胜负，草稿税按每次调用收取。

投机解码：草稿与验证分开

  • 投机解码把生成拆成两步：先起草一批候选 token，再让目标模型一次验证。草稿来源可以是已有文本，也可以是目标模型自己的预测，两种都不需要额外训练一个草稿模型。贪心验证保留目标模型的贪心输出；精确投机采样通过接受与修正流程保留目标模型的输出分布。
  • τ 是每次验证平均接受的草稿 token 数，不含目标模型在拒绝后或整段接受后额外给出的那个 token；命中率是查找返回草稿的尝试占比。
  • 加速比取决于每轮吐出的 token 数与起草加验证的耗时。训练好的草稿模型有个额外成本：不管命中与否，每次调用都要算一次，这就是草稿税；无模型草稿的猜测本身不花模型算力，税只在验证那一侧。

Prompt Lookup：从上下文里复制

  • 模型在摘要文档时，输出里很多内容已经出现在输入里。Prompt Lookup 把当前上下文窗口当语料库：取目标模型刚生成的最后 n 个 token，在上下文里找这个序列更早出现的位置，把后面跟着的 token 当草稿。n 越大，偶然匹配越少，但也越难找到匹配；搜索本身不产生额外模型推理。示例 n=3、k=10：线性扫描，第一个匹配胜出，复制后面最多 10 个 token。
  • 贪心验证按顺序接受复制的 token，到第一个不匹配处停下，再给出目标模型的修正 token；全部匹配则多给一个目标模型自己的 token。
  • 这种方法能成立，是因为很多生成任务的内容都来自输入：摘要复用源文的短语，文档问答引用原文段落，改代码时模型复制大段已有文件、只改几行。一次成功匹配可以在一轮验证里复制很多 token，τ 可以很高。vLLM 与 TensorRT-LLM 都把 Prompt Lookup 作为可选的提议器。
  • 命中率取决于任务与匹配设置。查找没命中只消耗搜索时间、不返回草稿；命中了，目标模型仍可能拒绝。Prompt Lookup 只能提议当前上下文里已经出现过的续写。

REST：从离线数据仓库取

  • REST 从离线建好的数据仓库里取草稿，仓库按目标任务选文本：编码模型用代码，助手用对话。它搜索当前 token 序列的后缀，从配置的最大长度开始，逐步缩短直到找到匹配。查找在 CPU 上跑，不需要额外模型推理。
  • 同一个后缀可以在仓库里出现很多次，检索可能返回多个续写。REST 把这些续写合并成一棵 trie，剪掉低频分支，剩下的树用树注意力一次验证。
  • 数据仓库可以比任何一个上下文窗口大几个数量级，所以 REST 能在 Prompt Lookup 找不到匹配的地方找到匹配。取回的片段来自真实文本，接受的匹配可以很长，τ 可以保持很高。
  • 猜测的好坏取决于语料：通用网络文本建的仓库会漏掉某个代码库的惯用写法，代码仓库对医疗对话没有用处。仓库占磁盘空间，要和模型一起服务；仓库是提前建好的，没法适应当前会话里发生的事。

SuffixDecoding：复用自己的历史输出

  • Agent 类任务最可能重复的，是模型几步之前刚写过的文本：编码 Agent 在几次尝试里重写同一个函数，多步流水线每次迭代用几乎相同的参数调同一个工具。SuffixDecoding 的语料就是生成过程中产出的这些输出。
  • 它维护两棵后缀树。单请求树索引当前提示与已生成的 token，覆盖 Prompt Lookup 的范围；全局树索引之前请求的输出，覆盖 REST 数据仓库的一部分，区别是语料是系统自己的历史输出、不是外部收集的文本。全局树随系统服务流量生长，出现越频繁的文本在树里的计数越高。
  • SuffixDecoding 用几个长度的近期 token 序列同时匹配两棵树，每次匹配找出之前观察到的续写。它用出现次数给候选 token 打分，贪心地为每次匹配建一棵推测树；一棵树节点分数之和估计目标模型会接受多少 token。目标模型用树注意力一次验证分数最高的那棵树。
  • 推测树的大小按匹配模式的长度成比例封顶：匹配长，说明当前文本有精确先例，就多起草 token；匹配短，证据弱，就少起草。Prompt Lookup 与 REST 每次命中提议的数量大致相同。
  • 模型重复自己早先输出的一大段时，τ 可以非常高；输出是全新的内容时，小草稿限制了浪费的验证工作。混合方法在后缀草稿分数超过配置阈值时用后缀草稿，否则回退到 EAGLE-3 这类基于模型的草稿器。

Lookahead Decoding：用目标模型自己的预测当草稿

  • Lookahead Decoding 用每次目标模型调用更新一组临时 token 序列，同时验证之前调用留下的候选。它把连续更新得到的 token 拼成 n-gram，缓存续写、留待以后验证。走访用 trigram、前瞻位置 3 个、每调用最多 2 个缓存候选；验证用贪心解码。
  • 初始化：已确认前缀在 P 里，临时 token 在前瞻窗口里，缓存的续写在 pool 里（锚点 token 到二元续写集合的映射）；初始猜测从提示里采样。Jacobi 更新把目标模型的下一个 token 预测当作下一组猜测；第一次前向填满 trigram 需要的两个历史层，同时给出普通的下一个 token。
  • 解码循环：每次迭代先取最近确认 token 下缓存的最多 2 个续写；两个历史行在 P 之后组成三条前瞻路径，加上缓存的草稿；目标模型一次打包前向评估全部路径（共享 P，各自内部因果注意力，互相看不到对方的推测 token）；贪心验证逐个比对缓存的草稿，保留连续匹配，在第一个不匹配处接目标模型的修正 token，最长的验证续写获胜，没有草稿匹配时普通的下一个 token 仍是保底。
  • 每个新 trigram 由本次调用的锚点、一个保留的猜测与一个新鲜的目标模型预测拼成，存进 pool 供后续迭代。循环按实际吐出的 token 数推进历史。
  • 每次 Lookahead 调用比普通解码调用处理更多 token；每调用多接受几个 token 可以抵掉这部分额外延迟。小批量、内存受限的解码可能留有算力给推测位置；候选匹配差或 GPU 负载重会抵消收益。

后缀树：让查表从 O(n) 到 O(p)

  • 后缀解码每步在 token 序列里找最近的一段 token，再取该段 token 之前出现时后面跟着的 token。线性扫描每次查询要 O(n)；后缀树索引序列后，找长度 p 的模式只要 O(p)；取全部出现位置或构造草稿还要额外工作。
  • 每个子串都是某个后缀的前缀：序列 ABABC 的后缀是 ABABC、BABC、ABC、BC、C；模式 AB 是其中两个的前缀，所以出现两次。trie 把每个后缀存成从根出发的一条路径、每条边一个 token；后缀树把单孩子节点链压缩成一条标有整段子串的边，节点数从 O(n²) 降到 O(n)：每个内部节点至少两个孩子，n 个叶子的树最多 n−1 个内部节点；边标签存成下标对 (i, j)，O(1) 存储，总存储 O(n)。
  • 搜索停在匹配点：一个节点，或一条边中间的位置。AB 的匹配停在节点；BA 沿根的 B 边到节点，匹配该节点 ABC 边的第一个 token，停在边内一个 token 处。匹配点之下的每个叶子对应模式的一次出现，下面的路径就是这些出现的已记录续写：AB 之下的续写是 ABC 与 C；BA 之下唯一的续写是边上剩下的 BC。
  • 后缀解码在树里存出现次数：记 c(q) 为模式 q 的出现次数，示例里 c(AB)=2、c(ABA)=1、c(ABC)=1。token t 跟在模式 q 后面的经验概率，等于模式 q 后面跟 t 的出现次数，除以模式 q 有记录后继 token 的出现总次数；AB 处 A 与 C 的估计各是 1/2。一条候选路径的分数等于沿途各 token 经验概率的乘积；方法按分数贪心扩展推测树，每步加分数最高的续写 token，直到树达到预算；预算与匹配模式的长度成比例。
  • 单请求索引从提示的后缀树起步，每生成一个 token 加一个；每步重建要每个 token O(n)、每请求 O(n²)。Ukkonen 这类在线算法一次加一个 token，总建树时间线性；出现次数的维护还要结构更新之外的额外记账。

结语

  • 四种方法共用一个结构：草稿不经过模型，验证一次过；差别只在草稿从哪里来、查找成本是多少。选哪种，看输出长什么样：输出复用输入，用 Prompt Lookup；有现成的大语料，用 REST；Agent 反复写同一段，用 SuffixDecoding；没有外部语料、又想零成本拿到加速，用 Lookahead，前提是批量小、显存没跑满。
  • 无模型草稿的核心不在模型，而在“已经存在的东西”：上下文、数据仓库、历史输出、目标模型上一次的预测。查找、合并、打分、验证四步都不需要训练，代价只在验证那一侧。
  • 代价的另一面是上限：草稿只能提议已经存在的内容，找不到就是找不到；命中率、匹配长度、GPU 负载共同决定最后能快多少。草稿税按每次调用收取，与命中与否无关。
