SGLang megakernel：Muse Spark Open 的 ultrafast decoding

0. 一句话：megakernel 是什么

SGLang 团队给 Muse Spark Open 从零写了一个 megakernel：每层 attention 加 MoE 只发一个 kernel。一个常驻 kernel 里，12 个 warp 各司其职，访存、计算与跨卡通信全程重叠。8 张 GB300 上，单请求解码从 517 tokens/s 冲到 1109 tokens/s（2.1 倍），每步 launch 从 1450 次降到 97 次，每步耗时从基线 12.9ms 降到 5.9ms。

背后的判断是：推理引擎的下一个形态可能不再是一串 kernel，而是一个常驻 GPU、自己调度自己的虚拟机——团队把 megakernel 称为"GPU 上的操作系统"。

1. 模型：Muse Spark Open 的一层长什么样

Muse Spark Open 是 MoE 模型，解码时每层要走 attention、MoE 专家、再回到下一层的 qkv 投影。传统做法是把每一小步拆成独立 kernel：RMSNorm、QKV 投影、attention、MoE dispatch、combine、输出投影……每步 1450 次 launch，每次 launch 都有固定开销，kernel 之间还要等前一个写完、下一个才能读。

megakernel 把切分点挪到"一层 attention 到下一层 qkv"：一层只发一次 kernel，144 个 SM 各驻一个 12 warp 的 block，KV 预取、权重预取、tensor core 计算、指令缓存预热与 NVLink 收发并行。

2. 12 个 warp，各有分工

一个 block 里的 12 个 warp 不是齐步走，而是分工协作：

  • 访存 warp：提前把下一层要用的权重与 KV 预取进各级缓存；
  • 计算 warp：tensor core 跑 GEMM 与 attention；
  • 通信 warp：管跨卡的 NVLink 收发，专家交换的数据在后台流动；
  • 同步 warp：用轮询与 flag 做跨 GPU 握手，不用系统级 fence。

分工的意义在于重叠：profiling 显示 GEMM 2 在 GEMM 1 结束前就已启动，权重流式传输、计算与通信在同一时间片里发生。

3. 权重预取要分层

权重不依赖上一层，warp 0 可以在当前操作还没完成时就开始预取下一层权重。预取分层走：

  • L2 层面的大块搬运；
  • SM 共享内存层面的分块；
  • 寄存器层面的最后一级。

关键点是预取不能抢计算的带宽：流式传权重时，一次轮询的加载要排在 bulk 拷贝后面 1.0-2.6µs；空转的 warp 还会抢干活 warp 的发射槽位与内存请求。忙等不理想，但硬件只给了这个办法。

4. 指令缓存：大 kernel 的诅咒

单个 SM 只缓存约 128KB 指令，而 megakernel 有 215-314KB。kernel 一大，指令缓存未命中就成了减速项。破局办法有三件套：

  1. 每 launch 把代码当数据读进 L2 预热；
  2. 循环不展开，控制代码体积；
  3. dry-run：先跑一遍把指令缓存热起来。

教训是：指令缓存要当作稀缺资源管，kernel 越大越要算这笔账。

5. 同步不用 fence，数据即 flag

跨 GPU 握手不用系统级 fence。教科书式的跨卡交接是"写数据、发一条内存 fence、再发 flag"，每次 fence 要 3.6-4.0µs。megakernel 的做法是：接收槽位先填永不出现的特殊值，数据本身就是 flag——读端看到特殊值消失，就知道数据到了。

  • SM 内轮询要 141-145ns；
  • 同一节点内两张卡之间的单向 flag 约 1.9µs；
  • 专家交换的缓冲区有两份，逐层轮换：空闲的那份在另一份使用时被重置为"空"；其余交接的槽位由读端用完后立即重置。

每层只需一次 fence，而且不在关键路径上。

6. 推测解码：草稿模型也 megakernel 化

megakernel 的验证步每步验证 16 个 token、平均接受 6.6 个。对比小米的 MiMo-V2.5-Pro：每步验证 8 个 token、平均接受 6.3 个，已经冲过 1000 tokens/s。16 个 token 验证起来更贵、会激活更多专家，但实测下来，用 16 个 token 拿到这个接受长度，比用 8 个更划算。

草稿模型本身也用同样的思路激进融合：SGLang 原来把草稿模型跑成 175 个 kernel，5 层每层一次 launch 后，草稿模型快了 2.6 倍，每步从 1.16ms 降到 440µs。

7. 性能：一步解码的耗时对比

基线 megakernel
每步总耗时 12.9ms 5.9ms
草稿 1.16ms 0.44ms
验证 10.9ms 5.3ms
kernel 数 1450 97

单请求解码 517 → 1109 tokens/s。整个 megakernel 的代码约 8000 行 CUDA 加 PTX。

8. 边界与下一步

团队把边界说得很清楚：

  • 今天只支持 batch size 1。批量放大后，等待会被就绪的活盖住，优化的重心会变；
  • 做到"GPU 上的操作系统"那一步，调度要在运行时决定哪个 warp 跑什么，而不是编译时定死。

三条可复用的判断：kernel 该在"一层 attention 到下一层 qkv"处切开；预取要分层、指令缓存要当作稀缺资源管；跨卡同步能不用 fence 就不用 fence。
