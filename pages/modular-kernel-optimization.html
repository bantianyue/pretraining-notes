0. 一句话总览

Kernel 优化回答的是"单个算子在 GPU 上跑多快"，系统优化（batching/caching/routing）回答的是"请求在整体 serving 架构里流得多顺"——两层都重要，但解决的是不同问题。Kernel 层是上面一切的天花板：kernel 不行，runtime 再怎么调也补不回来。

1. 什么是 kernel 优化

LLM 每生成一个 token，GPU 执行一串高度并行的操作：矩阵乘、attention、归一化、激活函数。这些操作由 GPU kernel 实现（同时跑在大量线程上的函数）。多个操作可以融合成一个 kernel——这是最有效的优化手段之一。

Kernel 优化 = 让这些函数跑得更快更省，手段：降延迟、提硬件利用率（计算单元/显存带宽）、减少数据搬运。

两条路线：

  • 手写 kernel：CUDA 或 Triton 等 DSL 直接写调。控制粒度最细（访存模式、线程排布、计算调度），但需要深厚的 GPU 架构功底。Triton 是折中：tile-based 编程模型藏掉了 warp 管理、shared memory 调度等细节，比裸 CUDA 好写，但控制力介于 CUDA 和纯编译器之间。
  • 编译器驱动：TVM、XLA 等从高层计算描述自动生成优化 kernel（融合、重排、自动调优）。门槛低，但对新架构/新算子模式跟进慢，峰值性能通常打不过手写。

Kernel fusion（核融合）的例子

y = silu(h + bias) * scale：

  • 不融合：3 次 kernel launch，6 次 HBM 往返；
  • 融合：1 次 launch，2 次 HBM 往返，中间结果不出片上内存。

HBM ↔ 片上内存的搬运远贵于计算本身——融合的本质是减少 HBM round-trip。

为什么大多数团队不碰这一层

vLLM / SGLang / TensorRT-LLM 把 kernel 全抽象掉了。但这层决定天花板：

  1. 新架构需要新 kernel：新 attention 机制、新 tensor 形状出来，不是"用 PyTorch 写出来"就行，得有人写出高效 kernel 并集成进框架，否则框架只能回退到慢速通用实现，甚至不支持。FlashAttention 就是典型：它不是某个推理框架发明的，是独立的 kernel 优化，证明价值后被框架收编。
  2. 性能天花板真实存在：框架只是 kernel 集合上的编排层，推理速度超不过底层 kernel 允许的上限。
  3. 硬件可移植性：手写 CUDA kernel 锁死 NVIDIA；想上 AMD/其他加速器就得重写。这就是可移植层和编译器方案越来越重要的原因（峰值性能 vs 可移植性的 trade-off）。

2. 工具选型：控制力的阶梯

从顶到底：cuBLAS/cuDNN（vendor 库）→ TVM/XLA（AI 编译器）→ Triton（kernel DSL）→ 手写 CUDA kernel；Mojo/MAX 想把语言+编译器+runtime+kernel 做成垂直整合的一整栈，打破分层边界。

越往下走：控制力↑、需要的 GPU 功底和工程时间↑、免费的可移植性↓。

层 代表 优点 局限
Vendor 库 cuBLAS/cuDNN 常见算子开箱即强，继承 NVIDIA 按代调优（Ampere/Hopper） 只覆盖已知 pattern；库边界之间难做跨算子融合；锁 NVIDIA
AI 编译器 TVM（auto-tuning 暴力搜 tile/schedule）、XLA/OpenXLA 自动融合、版图优化、跨硬件 峰值难打过手写/Tensor Core 利用不足；TVM 生态碎片化、auto-tuning 编译慢；GenAI 新算子跟不上
Kernel DSL Triton tile 模型好写，适合自定义 attention、fused pointwise 调试难、调优不自动、可移植性看后端成熟度
手写 kernel CUDA 极致控制，FlashAttention 诞生地 开发贵、难维护（换代即失效）、硬件锁死
全栈 Mojo + MAX 一门语言从模型写到 kernel；MLIR 编译到多后端（warp 同步、Tensor Core 指令按目标生成），写一次跑 NVIDIA/AMD/Apple GPU 生态成熟度待验证

选型流程（原文建议）：算子是标准的 → 先用 vendor 库/框架自带；图级别能消 HBM 往返 → AI 编译器；要自定义 kernel 但不想写 CUDA C++ → Triton；要 kernel 级控制 + 跨硬件可移植 → Mojo/MAX；关键瓶颈要在特定硬件榨干 → 手写 CUDA。

3. FlashAttention：kernel 优化的标杆案例

标准 attention 是 memory-bound：N×N 的 attention 矩阵要写回 HBM 再读回来，16K token 的内存是 1K 的 256 倍，大部分时间在等数据搬运，不是计算。

FlashAttention 的两招：

  1. Tiling + 重算：把计算切成能塞进 SRAM 的块，Q/K/V tile 进 SRAM、整块算完、增量更新输出、中间结果直接丢——N×N 矩阵永远不在 HBM 里物化；
  2. Kernel fusion：matmul → softmax → matmul 融成一个 kernel，无 HBM 中间写、无多次 launch 开销。

效果：attention 快 2–4 倍，显存大降，上下文做到 128K+。版本演进：

版本 年份 要点
FA-1 2022 IO-aware tiled attention，首创
FA-2 2023 更好的 warp 级并行与任务划分，比 FA-1 快 2x
FA-3 2024 Hopper 优化（FP8/BF16 Tensor Core、异步执行、warp specialization），H100 上 740 TFLOPS（75% 利用率）
FA-4 2026 Blackwell 定制：全异步 MMA、更大 tile、软件模拟指数、tensor memory，B200 BF16 达 1613 TFLOPS/s（71% 利用率），用 CuTeDSL 编写（flash_attn.cute）

FA-4 的洞察：Blackwell 上 Tensor Core 快了很多，但 shared memory 带宽、SFU（softmax 指数单元）、寄存器压力没跟上——瓶颈转移了，优化要跟着硬件的不对称扩展走。

4. 与预训练学习的关联

  • 用户本就是 GPU kernel 优化深域（KernelAgent 等文章），这篇是推理侧 kernel 优化的系统入门，可与已有经验互补；
  • FlashAttention 同时是训练侧核心 kernel（torch.compile / torchtitan 都依赖），训练 attention 的显存墙（MLSysBook 里 1.1TB activation 的例子）正是被 FA 这类 kernel 优化缓解的；
  • 选型阶梯对训练同样适用：torchtitan 底层大量用 Triton kernel + torch inductor（编译器），和这里讲的工具栈是同一套。
