SGLang 接进 IBM Spyre：一周、两人、1500 行插件

  • 原文：Integrating SGLang into Spyre in Under a Week with AI（PyTorch 官方博客，2026-11-12）
  • 原文链接：https://pytorch.org/blog/integrating-sglang-into-spyre-in-under-a-week-with-ai/
  • 作者：IBM Spyre 加速器团队
  • 星级：4⭐（推理服务化、非 NVIDIA 硬件后端；机制是集成模式而非核优化，篇幅短）
  • 一句话要点：两人加 AI 编程智能体，不到一周把 SGLang 接进 IBM Spyre，插件约 1500 行；靠 PyTorch 已有的 Spyre 硬件支持与 SGLang 清晰的扩展点，吞吐是参考实现的 3.6 倍，与 vLLM 持平，RadixCache 前缀共享零改动接入。

背景：Spyre 与起点

Spyre 是 IBM 面向企业 AI 推理的加速器，经 torch-spyre 接入：torch-spyre 把 Spyre 注册成 PyTorch 设备，连上 torch.compile，经标准 PyTorch API 暴露硬件支持。

IBM 的 Spyre 团队想把 SGLang 的服务栈，包括内置的前缀共享，带给 Spyre 用户。两个人，借助 AI 编程智能体，不到一周就把 SGLang 接进 IBM Spyre，插件只有约 1500 行。关键在起点：PyTorch 里已有 Spyre 硬件支持，SGLang 的扩展点又分得清楚，复用硬件代码就行。

AI 编程智能体拿 PyTorch 里已有的 Spyre 算子实现当参考代码，按 SGLang 的后端接口改写集成代码；工作集中在把已有的硬件支持连到新的服务框架上。插件已随上游 SGLang 一起开源。

结果：3.6 倍，与 vLLM 持平

最初的 SGLang 集成花了两人不到一周。插件约 1500 行，建在 PyTorch 的编译器与可复用硬件支持之上。四个小补丁扩展了 SGLang 的后端支持：

  • 两个补丁让已有执行路径摆脱对 CUDA 的依赖。
  • 两个补丁把 Spyre 注册成支持的设备与不依赖 Triton 的注意力后端。

兼容性改动也能支持别的加速器，注册改动是 Spyre 专属的。

SGLang 在 Spyre 上达到参考 PyTorch 推理实现（用 torch-spyre）约 3.6 倍的吞吐。团队还在 Spyre 上对比了 SGLang 与 vLLM，用的模型是 Granite 3.3 8B 与 Gemma 4 26B A4B：在测过的负载上，SGLang 的性能与 vLLM 持平。图中数值归一化到 vLLM=1.0，越低越好：Granite 3.3 8B 上 SGLang 0.993（快 0.7%），Gemma 4 26B-A4B 上 1.008（vLLM 快 0.8%），TP/DP 4/1、batch 4。

为什么能这么快：扩展点分得清

编译器能用、推理服务器现成，加 SGLang 就成了一个聚焦的集成任务。PyTorch 与 torch.compile 提供了一个共享实现层：经 API 表达加速器功能，两个服务框架都能用。

SGLang 提供了清晰的连接点：平台注册、注意力后端、KV 池与算子分发，把集成拆成有界的任务，同时保住已有的调度器、请求处理与服务循环。参考代码来自已有的 vLLM Spyre 集成，包括它对加速器算子的 PyTorch 实现：这给 AI 编程智能体提供了 Spyre 硬件行为的具体代码，SGLang 的扩展点则定义了改写后的代码必须满足的接口。两者合起来，减少了智能体要推断的硬件细节与集成归属。

已有的 vLLM Spyre 后端约 3500 行，SGLang 插件约 1500 行。最初集成里，注意力基类提供了外围逻辑，Spyre 后端只需重写内层的缩放点积注意力算子；复用这个基类，解释了两个插件之间约三分之二的行数差。SGLang 与设备无关的 KV 池也只需要一次方法重写做缓冲创建；分配仍需走 PyTorch 处理，因为已有路径依赖 Triton。

复用 vLLM 实现：RadixCache 零改动

团队复用了 vLLM Spyre 集成的注意力代码，包括它怎么把输入分组进桶、怎么处理张量形状；也复用了它基于 PyTorch 的 KV 缓存分配方式。RMSNorm、SiLU、GeLU、旋转嵌入与线性层，则把已有的 Spyre 实现连到 SGLang 的算子分发上。

有些功能完全不需要 Spyre 专属工作。RadixCache 是个好例子：前缀共享完全在 SGLang 的调度器内部解决，执行到达加速器之前就已完成，已有的调度逻辑原样可用。

怎么用与展望

下面的例子假设 Spyre 运行时、torch-spyre、SGLang 插件与其兼容性补丁已安装并配置好：

import sglang as sgl

models = [
    "ibm-ai-platform/micro-g3.3-8b-instruct-1b",
    "mistralai/Ministral-8B-Instruct-2410",
]

for model in models:
    engine = sgl.Engine(
        model_path=model,
        device="spyre",
        attention_backend="spyre_paged",
        dtype="float16",
        page_size=64,
        max_running_requests=1,
        disable_cuda_graph=True,
    )

    try:
        output = engine.generate(
            "Why is the sky blue?",
            {"temperature": 0, "max_new_tokens": 64},
        )

        print(model, output["text"])

    finally:
        engine.shutdown()

展望三件事：未来几个月增加动态形状支持，减少今天要做的形状管理；今年晚些时候把 Triton 带到 Spyre，并在上面启用 RadixAttention，打开更多核优化的门；硬件支持留在 PyTorch 里，集成代码留在 SGLang 的扩展点上，未来的编译器与运行时改进就有一条进服务栈的路。

关键数字

  • 集成成本：不到一周、两个人、约 1500 行插件（vLLM Spyre 后端约 3500 行）。
  • 吞吐：相对参考的 torch-spyre 推理实现约 3.6 倍。
  • 与 vLLM 对比（归一化到 vLLM=1.0，越低越好）：Granite 3.3 8B 上 0.993（SGLang 快 0.7%），Gemma 4 26B-A4B 上 1.008（vLLM 快 0.8%），TP/DP 4/1、batch 4。
  • 行数差：注意力基类复用解释约 三分之二。
  • 补丁：4 个小补丁（2 个去 CUDA 依赖，2 个注册 Spyre 设备与注意力后端）。

与 SGLang-Neuron 的对照

同一天发布的两篇 SGLang 非 NVIDIA 后端文章，讲的是同一套思路的两面：SGLang-Neuron 是在 Trainium 上从零建后端（异步运行时、Megakernel、PD 分离、HiCache），Spyre 是把 SGLang 接进已有硬件支持（一周、1500 行）。共同点是分层：硬件支持留在 PyTorch 里（torch-spyre、TorchNeuron），服务框架只在扩展点上接线；不同点是工作量级：Neuron 是深耕一个后端，Spyre 是证明接线本身可以很轻。两篇合起来看，SGLang 的扩展点（平台注册、注意力后端、KV 池、算子分发）就是新加速器接入的通用接口。
